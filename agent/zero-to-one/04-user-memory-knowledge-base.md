# Javaer转Agent：用户记忆与知识库

上一篇[《上下文工程》](03-context-engineering.md)讨论了模型在一项任务中需要看到什么。现在把时间拉长：一次提问结束之后，下次应该继续使用哪些信息？同一个助手面对不同用户、不同项目和不同版本的资料，又该怎样找到适用的依据？

继续使用资料助手，可以把问题分成两类：

- 用户记忆：用户明确提供、允许保存，并且对后续任务有用的信息，例如某个项目使用的接口版本。
- 知识库：经过整理、能够检索和核对的项目资料，例如订单接口文档与公共分页约定。

它们最后都会成为某轮上下文的一部分，但来源、适用范围和更新方式需要分别管理。

本文参考[《深入理解 AI Agent》第三章「用户记忆和知识库」](https://bojieli.github.io/ai-agent-book/astro/book/chapter3/)，沿着用户记忆、检索增强生成、知识组织与更新展开。现有代码用作观察基础；长期记忆、向量检索及知识更新流程属于后续实现与实验内容。

## 0、先把已有能力和目标分清

本篇继续使用 [first-agent](first-agent/README.md)。它在一次请求内保留工具调用历史，每次新提问都会重新创建消息，没有跨请求保存的会话历史或用户长期记忆。

先以这个示例为起点，区分已有能力和后续目标：

| 对象 | 要解决的问题 | 当前示例的情况 |
|---|---|---|
| 本轮上下文 | 模型这一次调用需要什么 | 包含当前问题、规则及本次请求内已产生的工具历史 |
| 会话历史 | 怎样理解同一会话中的后续提问 | 当前主线尚未实现跨请求历史 |
| 用户长期记忆 | 新会话怎样取得获准保存的用户信息 | 尚未实现 |
| 项目知识库 | 怎样查到适用、可核对的项目资料 | 目前只有两份固定公开教学文档及标题搜索 |
| 可恢复任务状态 | 中断后从哪里继续，哪些动作已执行 | 尚未实现持久化检查点 |

保存聊天消息、维护用户记忆和恢复业务任务，分别需要自己的数据与验证。后续增加存储时，应明确保存对象、读取范围和有效期。

## 1、从当前任务走向用户记忆

### 1.1 先核对当前请求的信息边界

当前 [DocAgent.java](first-agent/src/main/java/example/agent/service/DocAgent.java) 的 HTTP 处理入口调用引导阶段 3：

```java
public AgentResultDTO process(AskDTO request) {
    return run(request.question(), 3);
}
```

每次执行都会重新构建初始请求：

```java
var prompt = new Prompt(initialMessages(question, stage), options);
```

在阶段 3，`initialMessages` 只创建系统规则和本次问题对应的消息。工具执行后的 `conversationHistory()` 用于本次请求的后续循环；下一次 HTTP 请求会从新的初始消息开始。

可以按 [first-agent 运行说明](first-agent/README.md)启动服务，先提出一个完整的分页问题，再单独提交依赖上文的追问。调试时核对两次请求的初始消息，以及各自实际读取的资料。

判断依据是实际发送的消息和工具轨迹。即使第二次回答碰巧正确，也可能来自模型推测或重新检索，不能据此认定保存了前一次请求的信息。本文尚未执行这组真实模型实验。

### 1.2 长期记忆需要重新选择信息

一段对话里可能混有明确事实、临时要求、推测、工具结果和模型错误。把全部内容复制到下一次请求，会同时复制这些差异。

对于资料助手，可以用以下分类开始设计：

| 候选内容 | 应考虑的处理方式 |
|---|---|
| 用户明确说某个项目使用 v2 | 记录项目范围和原始来源；需要长期保存时按约定写入 |
| 用户只要求本次回答简短 | 先按本次任务处理，不自动提升为长期偏好 |
| 模型猜测用户大概使用 v2 | 保持为未确认推测，不保存成项目事实 |
| 工具返回分页约定 | 保留为知识来源；是否再次使用取决于版本和适用范围 |
| 某次搜索没有命中 | 可用于当前任务诊断，不一定值得进入用户长期记忆 |

记忆的目标是为未来任务提供有用、可核对的信息。内容是否值得保存，应结合用户要求和项目规则确定。

### 1.3 先定义怎样评估，再选择存储

参考书将记忆能力从基础回忆扩展到跨会话关联和主动帮助。对当前学习项目，可以先落实更容易核验的检查：

- 能否取回用户明确提供的信息。
- 换会话后能否按正确用户和项目取回。
- 用户修正后能否使用新信息。
- 信息不确定或冲突时能否说明缺口。
- 删除后是否停止继续使用。

主动建议可以后续再做。记住一条信息，并不表示助手获得了代替用户执行外部操作的授权。

## 2、设计记忆的写入与读取过程

### 2.1 先提取候选，再决定是否保存

可以把后续实现拆成以下过程：

```text
取得本轮对话与来源
  → 提取可能有长期价值的信息
  → 检查主体、项目范围、确定程度与保存依据
  → 与已有记忆比较
  → 按约定新增、修正、保留冲突或忽略
  → 为变更记录来源
```

提取可以使用模型，字段格式、主体归属和写入范围应由应用检查。即使模型返回了结构化 JSON，也仍可能错误归因或遗漏否定条件。

例如，「这个项目暂时还没确定是不是 v2」不能被提取成「项目使用 v2」。来源文本和候选记忆应能一起审查。

### 2.2 用一个有边界的记录表示事实

下面是拟新增的教学记录格式，不是现有数据库表，也不是用户的真实资料：

```json
{
  "subjectId": "test-user-a",
  "scope": "project:order-demo",
  "key": "apiVersion",
  "value": "v2",
  "source": {
    "type": "explicit-user-statement",
    "conversationId": "test-session-a",
    "messageId": "test-message-1"
  },
  "status": "candidate"
}
```

这里用 `candidate` 表明还处于候选阶段。正式保存时，可以按实际要求补充观察时间、生效范围、更新版本或失效状态，时间值必须来自真实记录。

几个字段分别回答不同问题：

- `subjectId`：这条信息属于谁。
- `scope`：适用于哪个项目或场景。
- `key` 与 `value`：明确表达了什么。
- `source`：从哪次输入得到。
- `status`：当前能否使用，还是需要确认。

真实身份应从可信认证上下文取得，不能只相信模型生成的用户 ID。当前本机示例还没有这个认证入口。

### 2.3 怎样选择表示形式

| 表示形式 | 适合观察什么 | 需要付出的维护成本 |
|---|---|---|
| 一条事实一条记录 | 精确查询、局部修正与删除 | 需要保留事实之间的关联 |
| 段落摘要 | 保留一件事的背景和来龙去脉 | 单个属性变化时可能要重写段落 |
| 结构化卡片 | 按用户、项目、属性检索 | 需要处理字段扩展和无法归类的内容 |
| 带关系与来源的记录 | 区分同名对象、多项目和时间变化 | 更新与查询逻辑更复杂 |

可以先用少量可人工核对的记录验证行为，再决定文件、关系数据库或检索索引等存储方式。这里没有为项目预选数据库或新增依赖。

如果采用摘要，要保留关键实体、范围和来源。把「某个项目使用 v2」压成「用户用 v2」，就丢掉了项目边界。

### 2.4 读取也需要选择

新请求到来后，先确定当前可信身份与任务范围，再检索相关记忆。应用过滤失效或不适用的内容，将必要部分附带来源送入本轮上下文。

不要一次取出某个用户的全部历史。分页问题可能需要项目版本，不需要与任务无关的其他偏好。

读取出来的记忆仍然需要核对其确定程度。来源于用户明确声明、模型推测或旧工具输出的内容，不应被统一改写成无条件成立的系统规则。

## 3、更新、冲突与遗忘

### 3.1 新旧信息先比较对象和时间

假设教学用户先说明某项目使用 v2，后来又说该项目已经迁移。后续实现需要先确认：

- 两条消息是否指向同一个项目。
- 后一条是已发生事实、计划，还是假设。
- 新信息何时生效。
- 原记忆是否应失效，是否需要保留历史来源。

单凭「消息较新」不能解决所有冲突。不同项目的版本可以同时成立；迁移计划也不能立即覆盖当前版本。

### 3.2 用户记忆不能替代项目文档

「用户的项目使用 v2」用于选择查哪份文档；「v2 的 `pageSize` 最大为 100」来自教学分页约定。两个事实来自不同渠道。

若用户记忆与项目资料看似矛盾，先检查版本和适用范围。缺少依据时，指出冲突或继续查询。不要把用户的一次口头描述自动写回共享知识库。

同样，历史答案即使曾被保存，也不能替代原始资料的更新检查。生成过一次答案，不会让答案自动成为新的权威来源。

### 3.3 删除要覆盖后续读取路径

如果记忆已经进入摘要、搜索索引或缓存，删除主记录后还要检查这些派生内容。否则新会话仍可能取回已删除的信息。

学习时可以用合成数据验证：写入后取回，修正后再取回，删除后开启新会话查询。记录每一步实际从哪个存储或索引取得内容。

原始记录的保留、日志脱敏和删除范围，应按项目的数据规则确定。不要为了调试方便，把完整私有记忆复制进普通响应轨迹。

## 4、把项目资料组织成可查询的知识库

### 4.1 现有两份文档已经提供了最小起点

[first-agent 的 DocTools](first-agent/src/main/java/example/agent/tool/DocTools.java) 中只有：

| 文档 ID | 已有教学内容 |
|---|---|
| `order-api-v2` | 订单查询的分页参数遵循 `pagination-v2` |
| `pagination-v2` | `pageNo` 从 1 开始；`pageSize` 最大为 100；默认值未规定 |

这些是本项目的固定教学资料。当前搜索只检查标题是否包含关键词，读取才返回正文，没有向量索引。

从实现可以看出：`pageSize` 不在这两个标题中，直接用它进行标题搜索不会命中；用「分页」则可以定位公共约定。这个差异适合用来学习检索问题：检索结果不足，可能来自查询与索引字段不匹配。

### 4.2 RAG 的核心是让检索结果成为回答依据

检索增强生成（Retrieval-Augmented Generation，RAG）可以先理解为：

```text
用户问题
  → 取得适用资料
  → 将必要内容与来源放入上下文
  → 模型生成回答
  → 核对回答与资料
```

向量搜索是取得资料的一种方式。当前的标题搜索与按 ID 读取也能组成一个小型的检索增强过程；直接把两份全文放入请求的引导阶段则没有执行检索。

Spring AI 提供 RAG Advisor 与可组合的检索模块。具体接入前，需要确定检索策略、数据存储及依赖；现有示例没有因为引入了 Spring AI 就自动具有这些能力。[Spring AI RAG 文档](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)

### 4.3 先整理来源和元信息

资料入库之前，先回答：来自哪里、适用于什么、当前是否有效、谁有权读取。

对于现有文档，ID、标题和正文已经存在。扩展到真实资料时，可以按需要增加项目、版本、章节、更新时间和访问范围等元信息，字段值从实际来源取得。

用户问 v2 的规则时，检索应能限制适用范围。只有语义相似度、没有版本和权限约束，可能找到看起来相关但不能使用的内容。

## 5、文档分块与检索策略

### 5.1 分块要保留一个片段的完整含义

长文档通常需要按章节或段落拆成可检索片段。划分时先检查：片段能否独立说明对象、规则和适用条件。

现有分页正文很短，没有必要为了演示而强行切碎。如果把它拆成三个不关联的碎片：

```text
从 1 开始
最大为 100
默认值未规定
```

就丢掉了每个数值对应的字段。更合理的片段至少要保留字段名、条件和文档来源。

资料变长后，可以先按自然结构切分，再处理仍然过长的部分。块大小、重叠量和召回数量应根据材料与测试问题调整，不直接套用其他项目的参数。

### 5.2 关键词和向量分别怎样帮助检索

| 方法 | 值得验证的任务 | 要观察的限制 |
|---|---|---|
| 标题或关键词匹配 | 精确文档名、参数名、错误码 | 查询用词与资料不同可能漏检 |
| BM25 等词项检索 | 在全文中按词项相关程度排序 | 分词、词形及术语表达影响结果 |
| 稠密向量检索 | 用户用不同说法描述同一问题 | 相似内容未必符合版本或精确标识 |
| 混合检索 | 同时包含精确术语与自然语言描述 | 需要合并、去重并比较两路候选 |
| 重排序 | 已取得候选，进一步判断相关性 | 增加处理成本，无法找回完全未召回的资料 |

例如，「一页最多显示多少条订单」与「`pageSize` 上限」可能需要找到相同依据。可以将它们放进同一组实验，检查不同检索方式能否取得 `pagination-v2`。

向量相似度描述匹配程度，不直接等于事实可信度。最终仍需要检查正文和来源。

### 5.3 先测召回，再测生成

为每个测试问题标出需要哪些文档或片段。先看这些依据有没有进入候选，再检查是否送入上下文，最后才检查回答。

如果一个问题需要两份资料，只找到其中一份可能仍不足以回答。使用 Recall@k 时，应按「前 k 项中命中的相关条目数／标注的相关条目总数」计算，再说明怎样汇总多个问题；不能把任意命中一份都当作完整召回。

生成阶段则检查结论是否得到资料支持、引用是否准确、缺失信息是否被编造。两层记录有助于定位问题，避免把所有失败都归结为模型能力。

## 6、让知识保留结构，并允许按需追查

### 6.1 资料之间的关系本身就是信息

现有订单文档指向公共分页约定。这个引用关系告诉助手还应到哪里找依据。

随着资料增多，可以保留目录、章节、父文档和交叉引用，让助手从索引逐步找到正文。搜索结果最好能帮助定位，而不是只返回一组脱离原文的句子。

不必一开始就建设复杂知识图谱。先检查现有引用能否解析、目标文档是否存在、版本是否一致，再决定是否需要更复杂的组织形式。

### 6.2 给片段补充必要的背景

一个片段只写「最大为 100」，即使被召回，也缺少对象。可以在索引时保留文档标题、章节和字段，帮助解释它属于哪条规则。

如果背景说明由模型生成，应与原文一起核对。生成的描述不能悄悄新增原文没有的默认值或适用条件，原始来源也要能回读。

### 6.3 让 Agent 根据反馈继续查询

当前两个工具已经体现了这种过程：

```text
搜索定位文档
  → 读取正文
  → 发现另一份约定的引用
  → 必要时继续读取
  → 汇总答案和来源
```

这只是一个可能路径，实际动作由模型根据反馈选择。应用继续负责工具校验、权限和预算。

如果资料缺失，应明确返回缺失；如果已经重复查询而没有新信息，应检查检索条件与任务状态。增加工具次数不能自动解决缺少文档的问题。

检索工具化之后，助手可以改写查询或跟随引用；相应地，也要记录每次选择带来了什么新依据。能多查几次，不等于最终答案更可靠。

## 7、知识更新怎样影响下一次回答

### 7.1 一次文档变化会影响哪些对象

当项目文档更新时，可能同时涉及原文、片段、检索索引、摘要和答案缓存。

可以先建立稳定的文档标识与版本关系，再让每份派生内容能追溯到对应来源。更新流程需要检查旧内容是否仍然会被检索到，已删除的资料是否仍留在派生结果中。

已有教学文档只有 v2。后续版本冲突实验需要另行准备和标记教学材料，不能把本文的更新流程描述成当前已经存在多个版本。

### 7.2 增量更新与整理分别做什么

增量更新处理新出现的资料或明确修正；整理处理重复、过期、断链和冲突。可以分别安排，但每次修改都要保留依据和验证范围。

对于共享项目知识，先形成可审查的差异，再按项目流程发布。对于用户记忆，则依据其授权范围和隐私要求处理。存储方式、审批方式与保留策略需要结合真实项目确定。

不要让一次模型回答直接覆盖原始文档。可以把回答中发现的问题作为待核对事项，回到来源确认后再更新。

### 7.3 更新后复跑相同问题

至少重新检查：

- 新资料是否能被检索。
- 旧版本是否按适用范围区分。
- 引用是否仍指向实际使用的内容。
- 无权读取或已经删除的资料是否仍会返回。
- 用户长期记忆是否影响了错误的项目或版本。

更新成功不仅是文件或索引写入成功，还包括后续查询能够使用正确内容。

## 8、按现有项目逐步做实验

以下顺序用于安排后续实现。请求边界与标题检索基线可从 `first-agent` 观察；记忆读写、新检索方式和资料更新需要增加相应能力或测试材料。

| 步骤 | 实验内容 | 需要保留的证据 |
|---|---|---|
| 1：请求边界 | 核对 `first-agent` 每次请求新建消息，以及本次工具历史的回填 | 两次请求各自的初始消息与工具轨迹 |
| 2：一条明确记忆 | 用合成用户输入保存一个项目属性，开启新会话读取 | 原始声明、保存结果、读取范围 |
| 3：修正与删除 | 修正该属性，再删除并重新查询 | 每次变更来源及后续读取结果 |
| 4：检索基线 | 对现有标题搜索记录命中与漏检 | 查询、候选和实际正文 |
| 5：分块与新检索 | 取得有来源的长材料后，增加一种检索方式 | 材料版本、片段和相同问题的对照 |
| 6：引用与版本 | 准备明确的版本材料，检查跨文档引用 | 适用范围与每条结论的来源 |
| 7：更新链路 | 修改或移除测试资料后重新查询 | 原文、索引及派生内容的一致性 |

首次实现长期记忆时，先选择少量可人工检查的信息。存储方案确定后，再增加持久化、并发更新、身份隔离等代码。

本篇没有新增用户记忆服务、数据库表、检索索引或写入接口。也没有执行真实模型实验；不能据此报告召回率、跨会话成功率或记忆已持久化。

## 9、给学习结果设定可核对的标准

| 场景 | 应验证的行为 |
|---|---|
| 用户明确提供项目版本 | 能保留对象、范围和来源 |
| 用户没有提供版本 | 不从常见做法推断 |
| 同一用户有多个项目 | 按当前项目检索；指代不清时追问 |
| 用户修正信息 | 区分已生效修改与未来计划 |
| 用户要求删除记忆 | 新会话及相关派生读取路径不再使用 |
| 文档没有默认值 | 明确报告未规定 |
| 搜索只找到标题 | 继续取得正文后才给出事实结论 |
| 资料存在版本冲突 | 核对范围并说明冲突 |
| 当前身份无权读取资料 | 搜索与读取路径都受到授权检查 |
| 工具失败或预算耗尽 | 返回实际状态，不伪造读取结果 |

学习记录要能够回答：信息从哪里来、为什么保存、为什么这次取出、怎样知道仍然适用，以及何时应停止使用。

到这里，资料助手的学习主线就从一次工具调用延伸到了信息的完整生命周期：当前任务里组织上下文，跨任务保存必要记忆，再从持续维护的知识来源中取得依据。
