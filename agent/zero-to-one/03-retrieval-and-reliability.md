# 03｜从“会调用工具”到“结果可验证”

[上一课](02-agent-loop-lab.md) · [返回总入口](README.md) · [下一课](04-study-plan.md)

本章把同一个只读资料助手逐步完善。以下是练习规格与设计示例，不是已经实现的完整应用。

## 1. 工具先把契约写清楚

工具说明决定模型如何理解能力，执行代码决定实际能做什么。二者要一致。

| 项目 | `search_notes` 的练习规格 |
|---|---|
| 用途 | 从明确允许的学习文档集合中检索资料 |
| 输入 | `query`：非空文本，最长 80 字符；不接受任意命令 |
| 输出 | 最多 5 个结果，每条含文档 ID、标题、来源路径、最多 500 字符摘要 |
| 无匹配 | 返回空结果集合；是成功检索，不是异常 |
| 错误 | 返回可识别的错误类型，不泄露堆栈、密钥或完整文件 |
| 副作用 | 无；只读 |
| 约束 | 不查 `.env`、凭据、业务记录，不接收任意绝对路径 |

第二个工具 `read_note(documentId)` 只接受搜索结果中的文档 ID，在执行端映射到白名单文件。不要把“模型说这个路径安全”当校验依据。

进阶到文件系统时：验证实际解析后的路径仍在允许根目录内，考虑符号链接或 Windows junction，限制读取长度，拒绝敏感文件。白名单 ID 比把整个 Shell 暴露出去更适合这个入门项目。

## 2. RAG 是给答案找依据

资料问答的一种简单流程：拿到问题，检索相关片段，把片段和问题一起交给模型，再输出带来源的回答。它不要求先有自主循环，也不一定需要向量数据库。

拿三条自编资料练习：

```text
doc-1：Agent Loop 会把工具返回加入下一轮输入。来源：课程 A。
doc-2：RAG 通过检索外部资料辅助生成回答。来源：课程 B。
doc-3：本练习的 Java Agent 学习入口在 study-notes/java-agent.md。来源：自编目录。
```

问题：“工具调用结果为什么要回填？”应优先找到 doc-1。问题：“RAG 是否自动训练模型参数？”检索到 doc-2 后，也不能仅凭它回答全部训练细节；检索到相关片段与片段足以支持结论是两步判断。

逐步增加难度：

1. 用关键词匹配建立基线。
2. 试“检索增强生成”和“RAG”这样的同义词，记录漏检。
3. 给一篇长文按标题分块，让每块保留来源与标题。
4. 只有漏检值得解决时，再比较向量检索或混合检索。

[All-in-RAG 教材](https://github.com/datawhalechina/all-in-rag) 可作为专题参考，按需选读。**Embedding** 是文本的数值表示，便于相似性检索；**Chunk** 是文档片段；**Rerank** 是对候选结果重新排序。相似并不等于正确，向量库不是事实裁判。

三个分开的验收问题：是否找到了正确资料？资料是否真的支持结论？最终答案是否忠实呈现并引用？不要只看回复是否通顺。

## 3. Context、State、Memory 分开记录

| 层次 | 保存什么 | 资料助手中的例子 |
|---|---|---|
| 模型上下文 | 当前调用要看的信息 | 当前问题、工具说明、相关片段 |
| 运行状态 | 本次任务的进度与控制数据 | 步数、取消标记、已查文档 ID |
| 会话记录 | 用户连续交互的消息与调用结果 | 第一次问 Agent，第二次问 Java 路线 |
| 长期记忆 | 有明确用途、可更正和删除的持久信息 | 用户确认“每周学习三小时” |

训练数据中的知识与以上四者也不同。保存了一条记忆，不等于它自动出现在下一次上下文；还需要选择、读取并提供给模型。

模拟一次上下文压缩：给助手十轮历史，其中第三轮说“只读、不要运行代码”，第八轮读过一份失效资料。请把历史压缩成：当前目标、明确约束、已确认事实及来源、尝试过什么、尚未解决什么。检查是否保留了只读限制、失效结论与证据。

不要只保留“我们讨论了 Agent”，也不要把未经验证的推测压缩成事实。压缩应在完整的调用与结果边界进行，避免保留一个找不到对应请求的工具结果。

## 4. MCP、Skill、框架分别补哪里

| 概念 | 解决的主要问题 | 不保证什么 |
|---|---|---|
| 本地 Tool | 提供某个可执行能力 | 不保证模型每次都选对 |
| MCP | 用统一协议连接工具、资源等能力 | 不自动赋予模型推理能力，也不自动完成业务授权 |
| Skill | 把某类任务的操作说明和可选资源组织起来 | 不等于隔离环境，可能携带可执行代码 |
| Agent 框架 | 封装消息、模型调用、循环和编排等通用机制 | 不替业务决定什么算成功 |
| Harness | 管理完整运行过程及周边能力 | 不能仅凭名字推断已具备沙箱或安全保障 |

MCP 概念以 [官方介绍](https://modelcontextprotocol.io/docs/getting-started/intro) 为准；实际字段需对照明确协议版本。先会本地工具调用，再将同一能力接成 MCP，你才能分清新增的是协议与连接，还是业务功能。

## 5. ReAct、计划与反思怎么选

**ReAct** 可以先理解为行动与观察交替：先搜资料，看结果，再决定读哪篇。本课关注可观察行为，不要求模型把内部思维链全部展示。

**Plan-and-Solve** 先生成任务表再执行，例如“查前置知识、查 Java 示例、整理计划”。计划不是铁律：某资料不存在时必须修订，而不是按错误假设继续。

**Reflection** 是检查初稿并尝试改进。在资料助手中，先用“来源路径是否存在”“引用是否支持答案”这样的外部检查；不要只让同一个模型夸自己答得好。为改进设置最多一次或两次的上限。

**多 Agent** 只有在职责或上下文隔离有明确收益时再试。先记录单 Agent 的失败基线，增加第二个 Agent 后，用同一批任务比较成功率、耗时和成本。任务拆分也可能增加沟通错误，不保证更聪明。

## 6. 失败处理必须能说清楚

以下数值是本课程的练习默认值，真实业务需要独立评估。

| 情况 | 如何识别 | 练习处理方式 |
|---|---|---|
| 检索无结果 | 成功响应但结果为空 | 换一次关键词或说明资料不足 |
| 参数错误 | 参数校验失败 | 反馈具体可修正点，禁止执行非法调用 |
| 工具不存在 / 越权 | 不在允许列表 | 拒绝并说明边界，不自动换成 Shell |
| 只读工具暂时失败 | 明确的超时或暂时性错误 | 最多重试一次；持续失败就说明未完成 |
| 持续循环 | 达到最多 6 次决策 | 停止并保留已获得证据，不冒充完成 |
| 单次调用超时 | 超过配置时限 | 结束等待或取消下游，说明该步未完成 |
| 用户取消 | 取消标记 | 不再启动新工具；记录在途操作的实际结果 |
| 输出格式正确但事实错误 | 引用不支持结论 | 评测不通过，检查检索或生成环节 |
| 资料里夹带指令 | 文档要求忽略规则、上传凭据等 | 当作不可信资料，执行端保持原有权限 |

只读不意味着没有隐私风险；读取密钥并交给模型也可能泄露。本课程练习使用公开、自编或已允许读取的学习资料。

## 7. 写操作留到后面学

本课不执行写文件、发消息、支付或数据库修改。如果将来工具存在副作用，需要另行设计：

- 幂等：相同业务操作重试不重复执行。工具调用 ID 的关联功能不能代替业务幂等键。
- 事务：本地数据库事务不能自动覆盖外部 HTTP 动作；不能长期持有事务等待模型推理。
- 状态：至少区分待确认、执行中、成功、失败和结果未知，不能把超时直接当“未执行”。
- 补偿与回滚：按外部系统真实能力设计，发送成功的消息等操作未必能撤销。
- 授权与审计：操作对象、参数、审批范围、实际结果都要可追溯；模型文字不构成授权。

这些是未来扩展的边界，不是本套离线代码已实现的能力。

## 8. 建立最小评测记录

每道题记录问题、允许来源、预期行为、实际工具轨迹、最终答案、是否通过。真实模型可以对相同题重复三次，观察波动；固定脚本通过三次仍不说明模型可靠。

任务通过率 = 完全满足该题验收项的任务数 / 总任务数。

引用支持率 = 经人工核对确实支持结论的引用数 / 总引用数；没有引用时标为“不适用”，不能自动算 100%。另记越权执行次数、耗时和 Token 用量，不要把多项指标混成一个“准确率”。

官方关于评测的延伸阅读见 [OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。本课程的题目与门槛见下一章。
