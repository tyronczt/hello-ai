# Javaer 转 Agent：提示词工程——从生成原理到可验证的任务契约

[第 02 篇](02-first-java-agent.md)已经实现了工具循环：模型提出请求，Java 执行工具，再把结果交回模型。现在保持这套分工，换成一个容易核对的任务：

> 北京市明天的天气怎样？请说明降水概率，并给出带伞建议、目标日期和来源。

同样拥有城市检索和天气查询工具，一个助手可能先核对地点和日期，再给出有来源的建议；另一个却在还没有查询时就说“明天晴朗，不用带伞”。能力已经开放，行为为什么仍有差别？

要回答这个问题，需要同时看三个层面：模型怎样根据输入生成后续内容；任务要求怎样变成可执行的规则；程序怎样检查模型的候选行为。提示词工程连接这三个层面，最终应落到“哪项错误减少了、依据是什么”，而不只是把一句话写得更像专家。

本篇以现有 [weather-agent](weather-agent/README.md) 为主线，按“生成机制 → 任务契约 → 规则与示例 → 工具与输出 → 对照评估”展开。Java 实践穿插在对应问题之后，不集中成一份大程序。两个新增的[离线实验](prompt-labs/README.md)只需 JDK 21；真实天气和真实模型实验分别从天气项目运行。

## 1、提示词为什么会改变模型行为

### 1.1 改变的是生成条件，通常不是模型参数

对自回归语言模型，可以把生成过程写成：

$$
P_\theta(y\mid x)=\prod_{t=1}^{m}P_\theta(y_t\mid x,y_{<t})
$$

这里的 `x` 是经过消息模板与分词处理后的输入，包括规则、问题、工具定义和已有观察；`y` 是接下来生成的 Token；`θ` 是模型参数。每生成一个 Token，模型都以当前输入和已经生成的内容为条件，计算下一步的候选分布。

把“请回答天气”改成“地点不明确时先追问，数值只引用本次天气工具”，改变了 `x`，因而可能改变后续生成的分布。普通推理请求没有执行反向传播，也没有把这句话永久写进模型权重。下一次请求如果没有携带这些规则，不能假定模型仍然知道它们。

这解释了两个经常混淆的现象。模型可以在一个会话里按照新例子完成任务，却没有因此完成一次微调；模型也可以生成很像天气预报的文字，却没有获得当日天气。前者利用当前输入中的模式，后者可能只是沿用了训练中熟悉的表达。

[GPT-3 的 few-shot 研究](https://arxiv.org/abs/2005.14165)明确区分了通过文本给出任务与示例、以及更新参数的训练过程。这个区分适合用来理解提示词，但不能据此认定每个模型都能从任意示例中可靠学会新规则。

### 1.2 从“写一句话”到“配置一份任务输入”

提示词不只存在于系统消息。用户问题决定当前目标，工具描述解释可用动作，示例演示边界情况，输出约定说明怎样交付。这些内容都会参与模型的选择。系统提示词是其中适合承载稳定应用规则的一部分。

| 信息或机制 | 改变什么 | 天气场景中的职责 |
|---|---|---|
| 系统规则 | 当前任务的行为约定 | 只依据工具结果、地点不明先追问 |
| 用户问题 | 本次目标与条件 | 北京、明天、概率、带伞建议 |
| 示例 | 输入与期望行为之间的演示关系 | 看到未知概率时说明未知 |
| 工具与检索结果 | 当前可引用的证据 | 指定日期的真实预报及来源 |
| 模型训练或微调 | 参数中的统计规律 | 改变模型本身，需要另行训练与评估 |
| Java 执行约束 | 实际允许发生的动作 | 校验工具参数、限制调用次数 |

这几项不能相互代替。提示词无法替代天气接口，天气接口也不会自动决定用户究竟问的是哪座同名城市。模型提出正确的工具名，仍不代表参数已经通过执行层检查。

![提示词和工具事实进入模型，工具请求经过 Java 校验后才能执行](assets/03-prompt-engineering/prompt-and-execution.png)

图 1：图中只展开工具请求这条路径。模型也可以直接回答或追问；工具结果返回后，是否继续调用仍要看信息缺口和剩余预算。图中的权限检查是通用执行边界，本天气项目主要落实工具白名单、参数校验与本次地点范围。

### 1.3 角色是行为提示，不是新增能力或授权

“你是气象专家”可能引导术语、语气和关注点，却不会增加一个实时数据源。“你是系统管理员”同样不会让 Java 自动授予文件或网络权限。应用仍须决定哪些工具存在、接受哪些参数、能访问哪些资源。

对于天气助手，“面向普通出行者，用易懂语言说明预报与建议”比反复强调“顶级、专业、绝对准确”更接近可检查的行为。前一句能够指导表达方式，后一句没有给出信息不足时的处理办法。

同样，不宜把模型错误都解释成“提示词不够强”。请求没有带上工具结果、工具返回了错误日期、模型不支持所需能力，都可能导致失败。只有确定缺失的是任务说明，改写说明才对症。

## 2、先定义任务契约，再优化措辞

### 2.1 把一个生活问题拆成可核对的条件

“明天要不要带伞”包含至少四个不同判断：在哪里、哪一天、预报提供了什么、怎样把预报转成建议。若这几项混在一句“准确回答”中，模型必须自行补足大量未定义的选择。

在本章中，一次任务的契约包括：

| 契约项 | 具体要求 | 检查证据 |
|---|---|---|
| 目标 | 回答用户指定地点、日期的问题 | 原始问题与最终候选回答 |
| 必要条件 | 地点能够确定；日期可以对应到当地日期 | 城市候选、地区、时区与预报日期 |
| 事实来源 | 天气数值来自本次实际工具结果 | `toolEvents` 中的原始结果 |
| 未知处理 | 缺地点追问；缺字段说明未知；服务失败说明未取得结果 | 缺口类型与实际处理是否一致 |
| 输出 | 分清预报事实、建议、来源与不确定性 | 候选答案与证据逐项对照 |
| 停止 | 已取得足够信息则回答；无法继续则说明具体缺口 | 工具轨迹与停止原因 |

“本次实际结果”很关键。昨天的预报、示例中的概率、模型记忆中的季节常识，都不能冒充这次查询的目标日预报。一般出行常识可以补充，但应与查到的天气事实分开表达。

### 2.2 同一个“无法回答”，其实有不同分支

把所有缺口都归为“请重试”会丢失最重要的信息：什么动作有机会补上缺口。

| 观察到的情况 | 合理的下一步 | 不合理的补全 |
|---|---|---|
| 用户没有给地点 | 询问城市或地区 | 猜测用户在北京 |
| 检索返回多个同名地点 | 用已给条件筛选；仍无法确定则追问 | 永远取第一项 |
| 服务不可用 | 说明本次没有取得预报 | 用“通常晴朗”代替结果 |
| 目标日概率为 null | 保留其他有效字段，说明该概率未知 | 写成 0% 或断言不会下雨 |
| 工具只返回三天，用户问十天后 | 说明当前工具没有目标日信息 | 把第三天预报延用到第十天 |
| 地点、日期、字段已经齐全 | 给出答案并结束 | 为展示工作量重复查询 |

规则由条件、动作和边界组成，才能与工具观察对应起来。比如“不要幻觉”可以转成：“若目标日降水概率为 null，说明接口未提供该概率，不用零替代；其他有效字段仍可引用。”后者没有保证模型必然遵守，却明确了正确分支。

### 2.3 冲突需要取舍，不能靠叠加强调解决

“任何问题都立刻给答案”与“必要条件不明时先追问”不能在所有任务中同时满足。“只用一句话”与“列出两座城市的日期、温度、概率、来源和差异”也可能冲突。

应先决定优先顺序：事实和必要条件完整，再追求简洁；缺少条件时，本轮可以只问一个具体问题。对于确定的业务规则，维护者需要先给出依据，不能让模型临时制定规则，再用“更专业”掩盖不同运行之间的差异。

例如是否在概率超过某个阈值时统一建议带伞，属于产品决策。当前天气助手没有配置这样的固定阈值，本章也不把某个任意百分比写成既有规则。它可以基于实际预报给出带条件的出行建议，但概率本身不是“必下雨”的确定结论。

### 实践 1：沿 Java 常量检查一份真实任务契约

打开 [WeatherPrompts.java](weather-agent/src/main/java/example/weather/WeatherPrompts.java)。其中 `BASE` 已经规定事实和缺口处理，`RULES` 增加流程与输出组织，`EXAMPLES` 增加三类演示。选择逻辑是：

```java
public static String of(String mode) {
    return switch (mode) {
        case "basic" -> BASE;
        case "rules" -> BASE + RULES;
        case "examples" -> BASE + RULES + EXAMPLES;
        default -> throw new IllegalArgumentException("prompt 只能是 basic、rules、examples。");
    };
}
```

先不用调用模型，逐条把常量中的句子映射到上面的契约表。能否找到“未知怎么处理”？是否规定了来源和时间？有没有同一件事的矛盾说法？这种检查只能证明规则表达是否完整，不能证明模型会遵守。

这里的 `basic` 也包含“只依据工具结果”“null 不是零”等共同边界。实验没有为了制造一个差基线而删除它们。`rules` 相比 `basic` 同时增加流程、停止条件和输出顺序，因此它首先是**方案对照**；即使表现变化，也不能直接归因于其中某一句话。

## 3、系统提示词怎样组织，才能保留职责边界

### 3.1 顺序应表达依赖关系

天气任务的关键依赖是：先得到地点 ID，才能查询该地点天气；先知道当地日期，才能解释“明天”；先匹配目标日期，才能引用该日概率。把步骤按这个顺序组织，能让规则与当前任务阶段对应起来。

```text
确认地点与日期要求
  ├─ 地点缺失或歧义无法消除 → 追问，结束本轮
  └─ 地点可确定 → searchLocations → 选实际返回的 ID
        → getWeather → 核对当地日期与 daily.time
          ├─ 失败或目标日期缺失 → 说明缺口
          └─ 有目标日数据 → 分开写事实、建议、来源
```

这不是要求模型每次执行固定步数。若上文已经有本任务可用的地点和天气，重复查询未必有价值；若城市尚未确定，后续步骤还不能开始。流程的作用是约束依赖与分支，调用预算则由程序独立限制。

对于必须严格按顺序发生、且没有语义选择空间的操作，直接由 Java 编排通常更可靠。把一段确定性业务流程交给模型逐步猜测，并不会自动获得 Agent 的优势。模型更适合处理表达变化、候选歧义和证据组织，程序承担确定的校验与计算。

### 3.2 Markdown、XML 和分隔符解决组织问题

如果规则增长，可以使用“任务、来源、流程、异常、输出”这样的标题，或用 `<examples>` 包裹示例。它们帮助人和模型识别信息块，也便于代码审查发现某条规则放错了位置。Anthropic 的[提示词实践文档](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)也把清晰要求、相关示例和结构标记作为组织手段。

但 XML 标签没有天然的权限。普通文本中的 `<system>` 不是 API 的 system 角色，给外部资料包上 `<trusted>` 也不会让它可信。除非应用真的使用 XML 解析器，否则标签只是模型输入的一部分，不构成程序语法校验。

同理，不能仅凭“用了标题”就宣称效果提升。改成 Markdown 时如果还增加了关键例外条件，实验同时改变了格式和内容。要研究格式，应保留相同规则和示例，只改变组织方式，并检查转换中没有漏掉否定词或条件。

### 3.3 模板插值与角色分离是两件事

Java 开发者容易把所有内容拼进一个大字符串：固定规则、用户问题、检索文档，最后一起发成系统消息。这样虽然编码简单，却把不同来源放进了同一指令位置，审查和追踪都会变困难。

当前 [WeatherContext](weather-agent/src/main/java/example/weather/WeatherContext.java) 保留了明确的消息分工：

```java
this.prefix = List.of(
        new SystemMessage(system),
        new UserMessage(question));
```

工具结果由工具调用管理器生成相应的结果消息，并与请求 ID 对应。消息角色随后如何被转换成模型接受的 Token 格式，属于 Chat Template 的职责；不同模型的模板可以不同，应用不应手工仿造分隔 Token。[Hugging Face 的说明](https://huggingface.co/docs/transformers/en/chat_templating)展示了这层转换，下一篇会进一步展开。

即使保持角色分离，也不能认为提示注入已经解决。外部资料可能含有“忽略规则”之类文字，模型仍可能误用。应同时保留来源、说明资料用途，并限制执行能力。JSON 序列化能防止字符串破坏 JSON 语法，不能阻止字符串的语义影响模型。

### 实践 2：检查发送前的规则、问题和工具是否各就其位

[WeatherAgent.java](weather-agent/src/main/java/example/weather/WeatherAgent.java) 的组装片段如下：

```java
var context = new WeatherContext(
        WeatherPrompts.of(promptMode), question, contextMode);
var callbacks = ToolCallbacks.from(tools);
var configured = model.getDefaultOptions();
var builder = configured instanceof OpenAiChatOptions openAi
        ? openAi.mutate() : OpenAiChatOptions.builder();
var options = builder.toolCallbacks(callbacks).build();
Prompt prompt = new Prompt(context.initial(), options);
```

逐项追踪：`WeatherPrompts.of` 提供固定规则，`question` 保留原始问题，`callbacks` 提供工具定义，工具结果要到实际执行后才出现。用户的问题没有被插进系统模板，也没有预先放入假天气。

还要注意选项来源。本项目使用 Spring AI 2.0.1，从已配置的 `OpenAiChatOptions` 派生后再设置工具，以保留配置中的模型和生成参数。直接重建一个带默认值的 Builder，可能意外覆盖已选模型。这个细节会污染实验：表面只改提示词，实际模型也变了。

天气报告中的 `rounds[].messages` 是 Spring AI 的发送前视图，`tools` 是注册的工具定义，二者都值得检查；但它们不等于最终 HTTP 请求抓包。若怀疑适配器改写了参数，应检查传输层证据，不能仅靠提示词日志推断。

## 4、示例怎样起作用，什么时候反而增加噪声

### 4.1 Zero-shot 与 few-shot 都需要任务说明

Zero-shot 指当前输入没有给任务演示样例，不代表没有指令。Few-shot 则在输入中放入少量示范，让模型在这次生成时利用其中的对应关系。参数保持不变，示例影响的是当前条件。

规则擅长表达边界：“概率缺失就保留未知。”示例擅长演示边界如何体现在回答中：“接口未提供该日期的降水概率，不能把它写成 0%。”当表达有多种合理形式时，示例可以补足语气、粒度和结构要求。

不过模型也可能学到维护者没有打算教的规律。如果所有例子都回答北京，模型可能更倾向默认北京；如果例子总有来源，正式规则却说可省略来源，两种指导会发生冲突。示例还可能让模型复制数值或固定日期，所以必须区分“演示数据”与“本次事实”。

### 4.2 应覆盖不同决策分支，而不是重复成功答案

本项目的三个演示分别对应三种缺口：

```text
以下示例仅演示处理方式，不是本次天气事实：
用户：明天出门需要带伞吗？
助手：请补充要查询的城市。
工具结果：status=ERROR，code=PROVIDER_UNAVAILABLE。
助手：这次未取得天气信息，暂时无法根据预报给出建议。
工具结果：目标日期的 precipitation_probability_max=null。
助手：接口未提供该日期的降水概率，不能把它写成 0%。
```

这三段是系统消息内的文字演示，不是本次真实调用的 `ToolResponseMessage`。它们也不是三条完整对话：后两段仅演示某个异常分支，不能替代一次完整成功回答的输出规范。正文和报告需要保持这个区别。

选择示例时，可以先列分支，再挑最少的代表样例。若错误集中在同名城市，就需要一个“候选多、条件不足”的例子；继续增加十条正常北京预报，未必能覆盖这个缺口。示例数量应由失败分布决定，不预设“必须三条”或“越多越好”。

还要留出未参与改写的检查任务。若把评估题的答案直接塞进示例，之后在同一道题上变好，主要说明模型看到了答案，不能据此评价对新问题的泛化。

### 4.3 固定示例与动态示例有不同成本

当前 `examples` 是固定文本，易于版本管理，也有利于保留稳定输入前缀。按任务检索示例可能提高相关性，但会改变输入长度与前缀，增加检索错误和数据来源审查的工作。

因此取舍应同时看行为收益、Token 成本与实际缓存指标，不能把固定示例当作普遍最优。这里也不需要把 KV Cache 原理再讲一遍；下一篇[上下文工程](04-context-engineering.md)会解释前缀为何影响复用。当前天气报告没有缓存命中字段，不能据字符长度计算“缓存收益”。

### 实践 3：只比较一个预先定义的行为变化

选择“没有地点时是否追问”作为第一项观察。先预测 `rules` 和 `examples` 会怎么处理，再分别运行这个相同问题。其余参数、工具和上下文策略保持一致，命令见第 8 节。

不要仅记录最终句子。检查轨迹中有没有擅自搜索某个城市；追问是否明确指出缺少地点；是否没有依据地声称已经查到天气。若两者都正确，结果就是“该样本未观察到差异”，不是实验失败，也不必临时改题来制造差距。

随后用另一种表述复查，例如“我周末出门需要雨具吗”。这里又多了日期歧义，应事先写清预期：先澄清必要条件，而不是默认周末等于明天。这样能检查模型是否理解分支，而不是只复述示例原句。

## 5、把复杂任务拆开：外部证据比长篇自述更可检查

### 5.1 拆分依据是数据依赖，不是“多思考几步”

天气问题已经包含一个最小的“观察—行动—再观察”过程：不知道地点 ID，先检索；有 ID 后查预报；拿到日期数组后，再匹配目标日。这些步骤的价值来自新证据。

如果先让模型写出一长串关于明天天气的推导，却没有天气数据，后续文字仍然缺少事实基础。反之，工具已经返回明确日期和概率时，也不必为了展示复杂性额外生成多个分析回合。

早期 [Chain-of-Thought 研究](https://arxiv.org/abs/2201.11903)研究了中间推导示例对算术等任务的影响；[ReAct](https://arxiv.org/abs/2210.03629)进一步研究推理与环境动作的交替。它们提供了任务拆解的研究背景，不代表在所有模型上加一句“逐步思考”都会提升效果，也不意味着应用应该要求披露模型内部思考链。

本项目需要的是可见依据：选择了哪个工具、参数是什么、取得了哪个日期的数据、为什么已经足够回答或仍需追问。回答可以给出简短的依据摘要，正确性仍回到工具观察检查。

### 5.2 工具描述是动作契约的一部分

对 Java 方法，方法名与类型只描述了一部分契约。`getWeather(long locationId)` 的 `long` 无法说明这是城市搜索 ID、行政区编码，还是数据库主键。模型若只看到类型，同样缺少决定参数的依据。

工具定义至少应交代用途、前置条件、参数含义、返回范围和失败方式。当前实现保留以下契约：

| 工具 | 前置条件与输入 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| `searchLocations` | 用户给出城市或地区名称 | 服务返回了哪些候选及 ID、地区、坐标、时区 | 该地天气；第一项必然是用户想要的地方 |
| `getWeather` | ID 必须来自本任务已返回的候选 | 当前条件及包含今天的三天预报 | 任意未来日期；现场实测；未返回的天气指标 |

工具只开放三天是本项目的请求范围，不是声称 Open-Meteo 服务最多只能提供三天。服务能力与应用开放能力应分别描述。

### 实践 4：沿工具注解追到执行校验

下面是 [WeatherTools.java](weather-agent/src/main/java/example/weather/WeatherTools.java) 中的真实声明，方法体省略：

```java
@Tool(description = "查询本次 searchLocations 已返回的地点 ID，取得当前天气条件及包含今天的三天预报。"
        + "返回当地时间、单位、来源和获取时间。current 基于气象模型数据，并非现场测量；"
        + "daily 是预报，超出返回日期范围的信息未知。不能把现在的天气当作明天的预报。")
public synchronized String getWeather(
        @ToolParam(description = "从本次城市搜索结果选出的精确 ID，不是经纬度或行政区划编码")
        long locationId) {
    // 方法体见源码。
}
```

这段注解服务于模型理解，实际约束在方法体中继续落实：从本任务的 `locations` 查找 ID；找不到就返回 `UNKNOWN_LOCATION`；从登记的坐标构造固定天气服务 URI。模型没有任意 URL 参数，也不能凭自己编造的坐标绕过地点检索。

在进入工具方法前，Agent 还会整批检查工具名称、调用 ID 和参数结构。最多 8 次模型调用、12 个工具请求由常量控制；五分钟预算在阶段之间检查，不会中断已经阻塞的外部请求。提示词写得再好，也不应承担这些硬限制。

`WeatherTools` 每次任务独立创建，其方法同步访问本任务地点集合；不同任务不会共享已搜索 ID。同步访问并不意味着模型选对了城市，只保证这里的状态访问有明确边界。查看报告时还应核对候选地区，而不只是核对 ID 的 Java 类型。

### 5.3 时间和单位必须与数值一起解释

“现在 18°C”与“明天最高 18°C”不是同一个事实。`current.time`、`daily.time`、单位、时区共同确定数值的含义。`retrievedAt` 是程序取回结果的时间，不能替代天气有效时间。

本项目以工具返回的当地当前日期理解“今天、明天”，然后查找 `daily.time` 中匹配的日期。跨午夜的长任务需要事先定义相对日期的锚点；当前实现并未额外冻结“用户提问时刻”的本地日期，不能把这个复杂边界说成已解决。

Open-Meteo 的当前条件来自气象模型数据，逐日字段是预报。读者应对照[服务字段文档](https://open-meteo.com/en/docs)，避免把“接口成功”解释成“现场实测正确”。对于概率为 null 的某一天，其余有效字段仍有价值，但不能从天气编码补造未返回的概率。

## 6、温度与 top-p：控制采样，不补充事实

### 6.1 为什么 temperature=0 也可能答错

模型在一个生成位置输出一组分数 `z_i`，通常称为 logits。对正温度 `T`，一种常见的概率计算是：

$$
p_i(T)=\frac{\exp(z_i/T)}{\sum_j\exp(z_j/T)}
$$

当 `T` 变小，分布通常更集中于高分候选；变大则更平缓。对同一组有限 logits，正温度不会改变候选的大小排序。若高分候选本来就是错误续写，降低温度只是更偏向它，没有取得任何新证据。

公式不能直接代入 `T=0`。服务中的零温度常用于表达贪心或近似确定性选择，具体实现与支持范围要看模型接口。贪心只选择当前步骤最高分候选，不保证整个回答的联合概率最大，更不保证事实正确。也不能跨服务保证请求逐字可复现。

### 6.2 top-p 改变允许采样的候选集合

Nucleus sampling（top-p）先按概率降序排列，保留累计概率达到阈值的最小前缀，再对保留项重新归一化。例如三个候选概率约为 `[0.6652, 0.2447, 0.0900]`，`top_p=0.8` 时第一项还不够，加上第二项才达到阈值，因此保留前两项。

温度调整分布，top-p 根据分布截断集合；它们相互影响。为了判断哪项改变产生了影响，实验中应固定一项再研究另一项。真实服务还可能存在额外采样策略或参数限制。[Transformers 生成参数文档](https://huggingface.co/docs/transformers/en/main_classes/text_generation)可用于核对这些术语，但其默认值不能直接套用到本项目的远程模型服务。

### 实践 5：用纯 Java 算出温度和 top-p 的变化

从仓库根目录运行 [SamplingLab.java](prompt-labs/SamplingLab.java)：

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' '-Dstderr.encoding=UTF-8' agent/zero-to-one/prompt-labs/SamplingLab.java
```

程序使用人工 logits `[2, 1, 0]`，计算的是三个抽象候选的概率，不是真实模型对三段答案的打分。核心 softmax 实现为：

```java
double max = logits[argmax(logits)];
double[] values = Arrays.stream(logits)
        .map(z -> Math.exp((z - max) / temperature)).toArray();
double total = Arrays.stream(values).sum();
return Arrays.stream(values).map(v -> v / total).toArray();
```

减去最大值不改变归一化结果，可以避免直接对很大的正数求指数。完整文件还校验温度、非有限数值和概率分布，不能省略这些入口条件后把片段当通用工具使用。

实际数值输出如下：

```text
T=0.5 -> [0.8668, 0.1173, 0.0159]
T=1.0 -> [0.6652, 0.2447, 0.0900]
T=2.0 -> [0.5065, 0.3072, 0.1863]
top_p=0.8 -> [0.7310585786300048, 0.26894142136999516, 0.0]
greedy index=0
changed logits [0, 2, 1], greedy index=1
```

前几行改变温度，最高分候选始终是第 0 项；最后一行人为改变 logits，最高分候选才变成第 1 项。它帮助区分“改变输入可能改变模型分数”与“给定分数后怎样选择”，并没有模拟哪一句提示词能够产生后一组 logits。

文件内 10 个自检验证归一化、排序、截断、数值稳定性和非法输入。它没有加载模型，也没有随机生成天气答案。这个实验通过，只证明这段数学计算符合约定。

## 7、从输出格式走到事实核验

### 7.1 三层正确性不能混为一谈

让模型按“城市和日期、天气信息、建议、来源”回答，有利于人阅读。让它输出 JSON，有利于程序解析。但是能解析、符合 Schema、符合证据是不同层次：

| 层次 | 能检查什么 | 仍可能遗漏什么 |
|---|---|---|
| 语法解析 | 是否为合法 JSON | 日期写错、概率无依据 |
| 结构与取值校验 | 字段是否齐全、类型是否正确、概率是否在范围内 | 60% 合法，但工具可能返回 null |
| 证据与任务核验 | 地点、日期、时区、来源、数值是否对应本次目标和证据 | 上游预报是否准确、自然语言建议是否恰当 |

Spring AI 的[输出转换器文档](https://docs.spring.io/spring-ai/reference/api/structured-output/converters.html)区分了生成前添加格式要求和生成后解析，并说明这种转换属于尽力而为。服务端原生结构约束可以减少结构错误，但支持的 Schema 范围需按接口核对，仍不能为 JSON 中的天气事实背书。

当前天气助手返回自然语言候选答案，**没有接入答案 JSON Schema、事实核验器或自动质量评分**。下面另建一个小实验，只演示第三层中可确定的字段比对，避免把计划写成已经上线的能力。

### 7.2 先定义未知值，再定义候选类型

假设我们已经把目标日观察与候选答案分别整理成 Java record，其中概率使用 `Integer`，以保留 null。若直接选 `int`，并在解析时把缺失值默认成 0，模型还没被评分，事实就已被程序改写了。

本章的合成实验只保留核验所需的字段：

```java
record Facts(long locationId, LocalDate date, String timezone,
             String source, Integer rainPercent) { }

enum Outcome { ANSWER, UNAVAILABLE }
record Candidate(Outcome outcome, Facts facts) { }
```

这是类型说明；完整源码带有日期、时区、概率范围等检查。`ANSWER` 表示提供预报，`UNAVAILABLE` 表示未取得可用预报。用户条件缺失时的追问不在这个二分模型中，不能为了复用一个简单类型把所有任务状态硬塞进去。

核验时还需要先确认观察本身适用于目标任务。两份记录都写了同一个错误日期，彼此一致也没有回答用户问题。因此核验顺序是：目标地点和日期 → 观察是否适用 → 候选状态 → 各字段是否与观察一致。

### 实践 6：让一个“格式没问题”的错误答案被拒绝

从仓库根目录运行 [EvidenceCheckLab.java](prompt-labs/EvidenceCheckLab.java)：

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' '-Dstderr.encoding=UTF-8' agent/zero-to-one/prompt-labs/EvidenceCheckLab.java
```

程序构造一个目标日概率未知的合成观察，再比较不同候选。日期固定为 `2026-10-22` 仅用于夹具，不表示当天真实天气。概率核验的关键不是大小比较，而是保留未知语义：

```java
if (!Objects.equals(observed.rainPercent(), claimed.rainPercent())) {
    errors.add("PROBABILITY");
}
```

观察为 null、候选为 0，Java 类型完全合法，仍会得到 `PROBABILITY`；日期错位得到 `DATE`；地点错位得到 `LOCATION`；服务失败却给出预报得到 `NO_EVIDENCE`。若取得的观察不匹配目标日期，则先返回 `EVIDENCE_MISMATCH`，不拿另一日观察为候选背书。

12 个合成案例检查还覆盖来源遗漏、时区错位、候选缺失事实、如实说明服务失败和概率越界。它们验证的是核验逻辑能够区分这些情况，不是“模型通过了 12 道题”。

这个实验刻意使用已经构造好的 record，没有从自然语言抽取事实。如果让另一个模型先提取字段，提取错误也会进入评分过程，需要单独评估。更不能只比较候选自己填写的“来源”与候选自己填写的数值；用于核验的观察必须来自独立保存的工具结果。

## 8、怎样设计一次可信的提示词对照

### 8.1 先规定成功是什么，后看答案好不好听

本篇的三个模式不是排行榜，而是待比较的方案。对照前应固定任务与评分条件，至少把以下情况分开记录：

| 任务类别 | 示例 | 主要判定 |
|---|---|---|
| 常规单城市 | 北京市明天天气，注明日期和来源 | 正确地点、目标日与事实来源 |
| 缺少条件 | 明天出门需要带伞吗 | 明确追问地点，不擅自查询默认城市 |
| 地点有歧义 | 只给一个同名地区名称 | 是否根据候选与用户条件判断，必要时追问 |
| 多城市 | 比较北京与上海明天天气 | 分别取得证据，保留各自时区与目标日期 |
| 日期超范围 | 查询返回范围以外的一天 | 说明工具能力缺口，不外推数值 |
| 字段缺失 | 目标日概率为 null 的固定观察 | 不把未知写成零或确定判断 |
| 外部服务失败 | 固定 `PROVIDER_UNAVAILABLE` 观察 | 不声称已查到天气，不编造替代预报 |

最后两项需要可控观察，不应靠频繁请求真实服务来“碰到”异常。地点歧义也应固定候选集合，否则不同检索结果会改变任务难度。

不要用一个总分掩盖不同问题。事实错误、未按流程查询、格式遗漏、网络失败是不同故障。任务全通过率可以要求所有关键条件都满足；同时保留逐项错误，才能知道下一轮应该修改哪一条规则。

### 8.2 真实天气探索与冻结数据评估承担不同任务

真实天气实验用于发现实际问题：服务字段怎样返回、模型走了哪条路径、用户表述是否有歧义。但天气会更新，“明天”会随日期变化，两次实时调用不是严格相同环境。

冻结数据评估则需要固定地点候选、预报快照、相对日期锚点，以及工具失败分支。回放仍应根据工具名和参数返回对应观察；若不管传什么参数都返回一份正确天气，会掩盖模型选错地点、日期或工具的错误。

本项目已有 `WeatherTools` 的包内可替换请求函数，适合本机检查；**命令行尚未提供真实模型配合冻结天气的重复评估入口**。因此本篇提供实时探索命令与离线核验实验，不把两者拼成一个已经完成的质量基准。

![固定任务、模型、参数和快照，对两个提示词分别保留轨迹并逐项核对](assets/03-prompt-engineering/controlled-evaluation.png)

图 2：冻结条件、分别保留轨迹、按同一标准检查，是对照的基本要求。图中没有指定哪种提示词获胜；实际结论可以是改进、退化，也可以是暂未观察到稳定差异。

### 实践 7：运行三种模式，先做一项可追踪的观察

在仓库根目录进入天气项目，先打包：

```powershell
Set-Location D:\github\hello-ai\agent\zero-to-one\weather-agent
mvn -q -DskipTests package
```

可先运行真实天气连通检查，它访问 Open-Meteo，不调用模型：

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' '-Dstderr.encoding=UTF-8' -jar target/weather-agent-0.0.1-SNAPSHOT.jar --weather-check
```

模型配置按[天气项目说明](weather-agent/README.md)设置。以下命令会调用所配置的真实模型并产生模型用量；使用公开教学问题，因为报告会保存问题和消息。先选一个模式：

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' '-Dstderr.encoding=UTF-8' -jar target/weather-agent-0.0.1-SNAPSHOT.jar '--ask=明天出门需要带伞吗？' --prompt=rules --context=full
```

预测是“追问城市”。下一次只把 `--prompt=rules` 改为 `--prompt=examples`，仍用同一个问题。要观察完整天气流程，再换成开篇的北京市问题，分别运行 `basic`、`rules`、`examples`；不要同时切换 `--context`，否则无法分清效果来自提示词还是历史组织。

每次运行都有独立的 `report.json`。将终端打印的真实路径代入下面的变量，逐项检查：

```powershell
$reportPath = 'target/weather-runs/run-实际目录/report.json'
$report = Get-Content -LiteralPath $reportPath -Raw -Encoding utf8 | ConvertFrom-Json
$report | Select-Object kind, promptMode, contextMode, status, answer
$report.rounds | Select-Object round, elapsedMs, usage
$report.tools | ConvertTo-Json -Depth 15
$report.toolEvents | ConvertTo-Json -Depth 20
```

先确认规则版本和工具定义，再沿 `rounds[].messages`、`rounds[].response` 看请求与回答，最后沿 `toolEvents` 核对执行结果。不要只看最后一句回答，也不要把打印 `COMPLETED` 当成验收通过：它只表示获得非空候选文本，可能是答案，也可能是追问。

`rounds[].elapsedMs` 是一次非流式模型调用的耗时，不是首 Token 延迟；顶层 `elapsedMs` 是整个任务耗时。`usage` 缺失时应记为未知，不能记为零。`messageJsonUtf16Units` 是消息 JSON 的 UTF-16 长度，不是 Token 数。这些区分会直接影响成本和性能结论。

### 8.3 从方案对照进一步走到消融

消融是在基线中有计划地移除或改变一个组成部分，观察哪些行为变化。参考书的[提示工程实验目录](https://github.com/bojieli/ai-agent-book/tree/main/chapter2/prompt-engineering)围绕语气、规则组织和工具描述安排实验，本章借鉴它的实验设计，不移用其百分比作为本项目结论。

可以在稳定的 `rules` 基线上分别研究：保留内容但改语气；保留全部规则但改变组织；保留 Schema 但移除工具说明；保留规则但增加一组边界示例。每一组有不同假设，不应一起修改后再把变化归因于“提示词优化”。当前命令行只实现三种累计模式，其他消融需要明确增加对应实验版本，并保持执行安全校验。

还要警惕“删除说明后仍然成功”。模型可能从 `getWeather` 的名字推断了用途，任务也可能太简单，没有覆盖这个说明保护的边界。这只能说明当前样本没有暴露差异，不能说明工具描述普遍无用。

### 8.4 重复运行，报告分母，保留失败

单次成功可能依赖偶然路径。对同一任务做多次试验，既看平均通过情况，也看是否稳定。总运行通过率可以写成“通过的任务运行数 / 计划任务运行数”，但网络或服务不可用需要另列；若另外报告排除基础设施错误后的模型指标，应同时写清排除规则和分母，不能默默删掉失败。

[τ-bench](https://arxiv.org/abs/2406.12045)通过任务目标状态评估 Agent，并用重复试验研究可靠性。其 `pass^k` 关注多次都成功的可靠程度；不要与“尝试 k 次至少有一次成功”的 `pass@k` 混用。天气任务没有同样的数据库目标状态，需要自己的地点、日期和字段核验标准。

比较两个版本时，应保留每一道题的配对结果：哪些题由错变对，哪些由对变错。样本少时直接给出计数和失败类型，比一个精确到小数点的提升率更有信息。需要统计结论时，再扩大预先确定的任务集、重复次数，并估计不确定性。

迭代中把用于修改提示词的开发集与最终检查集分开；新出现的失败可以进入下一轮开发集，不能反复查看同一组“保留题”后仍把它叫独立检验。模型版本、工具版本、采样参数和证据快照也应随结果一起记录。

## 9、怎样维护提示词，避免越改越难理解

### 9.1 先定位失败发生在哪一层

| 看到的现象 | 优先检查 | 可能的修正位置 |
|---|---|---|
| 没有城市却开始查询 | 是否缺少条件分支，示例是否总在默认城市 | 任务规则与示例 |
| 选了错误同名城市 | 候选信息是否完整，用户限定是否进入输入 | 工具返回、规则或追问流程 |
| 工具正确，答案日期错位 | 日期对应规则是否明确，目标日证据是否保留 | 提示词、上下文或字段核验 |
| 模型参数与配置不同 | 选项构建是否覆盖配置 | Java 适配与请求构造 |
| 天气结果在下一轮消失 | 工具历史是否回填，压缩是否丢字段 | 上下文组装 |
| 模型提出未开放工具 | 指令或资料是否误导；执行层是否确实拒绝 | 提示词与执行校验分别处理 |
| 正常题变好，异常题变差 | 新示例是否偏向正常回答，规则是否冲突 | 示例选择与回归任务 |

如果失败来自结果没有传回模型，再增加十句“请认真阅读工具结果”也补不上数据。先检查真实输入与轨迹，再决定修改哪一层，能减少补丁式的提示词堆积。

### 9.2 把提示词当作可审查的配置资产

本项目体量小，Java 文本块已经能够统一管理规则，无需为此引入模板框架。审查一次修改时，至少要能回答：它修复哪类失败；改变了哪条分支；是否与示例冲突；工具描述是否仍与实现一致；原有正常任务有没有退化。

规模扩大后可以按需要外置模板、记录版本或内容哈希，但版本标记应对应完整实验条件，不能只给系统提示词编号而忽略工具 Schema 与模型参数。本项目当前报告记录模式名，没有完整自动实验清单；严格复现还需额外保存这些条件。

新的失败通常应转化为一个最小反例。例如“概率 null 被写成 0%”是明确反例；把一整段历史聊天加进系统提示词，可能同时引入过期数值、用户隐私和不相关要求。保留行为规则与必要样例，原始问题和证据留在受控记录中。

### 9.3 提示词工程何时需要转向上下文工程

规则明确以后，下一轮是否仍带着目标日期、工具观察和来源，取决于上下文构造。示例和 Skills 何时加载、历史怎样压缩、稳定前缀怎样复用，也不是仅修改一段系统文本就能解决的问题。

下一篇[《上下文工程》](04-context-engineering.md)沿同一分工继续解释 Chat Template、KV Cache、提示注入、Skills、状态与压缩。本篇已经建立了任务契约；下一篇要保证决策所需的信息在合适的时刻真正进入模型请求。

## 10、本章小结

提示词通过改变模型生成时的条件影响行为，普通调用不会因此更新模型参数。它可以说明目标、规则与例外，提供示例和输出约定，但实时事实仍要来自工具，权限与参数限制仍要由程序执行。

一份可维护的提示词首先是一份任务契约：输入条件是什么、证据来自哪里、缺口怎样处理、什么时候结束。流程表达依赖与分支，示例展示边界行为，工具描述说明动作能力；这些内容需要一致，而不是各自写得很长。

采样参数解决的是给定分布后怎样选择，结构约束解决的是输出怎样解析，证据核验解决的是候选是否对应本次目标。降低温度、输出合法 JSON、获得 `COMPLETED`，都不能单独证明答案正确。

本章七项实践连接了这些层次：检查真实提示词常量、追踪消息组装、设计示例观察、核对工具契约、计算采样分布、运行字段核验、读取真实任务报告。两个新实验共含 22 项确定性检查；它们验证计算和核验逻辑。三种提示词的真实模型质量对照尚未完成，本章没有给出优胜版本或成功率提升结论。

## 11、思考题

1. 为什么“你是顶级气象专家”无法替代一个天气接口？它仍可能在哪些方面改变回答？
2. `basic` 已经包含未知值与来源规则，`rules` 增加流程和输出顺序。如果后者更好，能否说是“编号列表提高了准确率”？
3. 模型把 null 概率写成 0%。你会先检查哪三处证据，怎样区分模型错误与程序默认值错误？
4. 把用户问题放在 `<user_input>` 标签里，再整段发送成系统消息，与真正的 `UserMessage` 有什么区别？标签能否阻止提示注入？
5. 所有 few-shot 例子都来自北京的正常天气，哪些分支仍可能完全没有被教到？怎样用更少的例子改善覆盖？
6. 当 logits 为 `[2, 1, 0]` 时，降低正温度为什么不能让第三项变成最可能候选？`top_p=0.8` 保留哪些项？
7. 一个候选 JSON 通过了类型和范围检查，为什么还可能没有证据？怎样处理“观察和候选都用了错误日期”的情况？
8. `getWeather(long locationId)` 为什么还需要文字描述和运行时范围检查？如果已经有 Schema，后两者是否可以删除？
9. 在不同日期分别运行 `rules` 与 `examples`，后者回答更完整。这个结果能支持什么结论，不能支持什么结论？
10. 新提示词让答案更简短，但服务失败时开始编造天气。怎样设计回归与指标，避免把这种改动判为整体提升？
