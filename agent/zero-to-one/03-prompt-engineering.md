# Javaer 转 Agent：提示词工程

[第 02 篇](02-first-java-agent.md)已经实现了文档助手：模型提出工具请求，Java 执行，再把结果交回模型。这个例子保留原样。从本篇开始，换一个更容易判断的生活问题：

> 北京市明天的天气怎样？请说明降水概率，并给出带伞建议、目标日期和来源。

我们使用新的 [weather-agent](weather-agent/README.md)，接入真实 Open-Meteo。它有城市检索和天气查询两个工具。用户的问题相同、工具也相同，为什么有的回答会查清日期和来源，有的回答却直接给出一句「建议带伞」？

工具提供了取得信息的能力，提示词还需要说明怎样使用这些能力、遇到缺口怎样处理，以及什么样的回答才算回应了问题。提示词工程从这里开始。

## 1、先分清要求与事实

### 1.1 「专业」不是一个可以检查的任务

「你是专业天气助手，请准确回答」表达了角色和期望，却没有说明查询对象、日期、数据来源和输出要求。模型仍要自行补齐这些选择。

对于当前问题，可以把任务拆成几个能核对的条件：地点是北京市；日期是当地明天；回答需要依据天气工具；降水概率与建议分开；来源和目标日期需要保留。这样才能从执行轨迹判断问题出在哪里。

角色仍然有作用，例如规定回答面向普通出行者，避免使用不必要的气象术语。但角色不会给模型增加实时天气，也不能把预测变成确定事实。即使把「专业」重复十次，缺失的天气结果仍然没有进入请求。

### 1.2 一段提示词里有几种不同的信息

| 内容 | 在天气任务中的作用 | 不应承担的职责 |
|---|---|---|
| 任务目标 | 回答指定城市、指定日期的天气问题 | 替用户补出没有提供的地点 |
| 处理流程 | 先检索地点，再查询天气并核对日期 | 强制每个问题都执行相同步数 |
| 事实边界 | 数值以本次实际工具结果为准 | 保证服务返回本身永远准确 |
| 输出要求 | 区分天气事实、建议、来源与缺口 | 保证格式正确就意味着事实正确 |
| 示例 | 演示怎样追问、说明失败或处理未知值 | 把示例中的城市、数值套到当前任务 |

提示词工程主要处理这些要求的表达与组合。温度、预报日期和概率等事实仍由工具提供。把真实天气值直接写进固定规则，会让规则很快过期，也使下一次运行难以分清数值究竟来自哪里。

### 1.3 先有通过条件，再谈优化

本篇的通过条件不是回答听起来更自信，而是能逐项找到依据：查询了正确地点；使用了目标日期对应的预报；没有把 null 写成零；服务失败时说明未取得信息；建议能够回到已经取得的天气事实。

这些条件也暴露了一个边界：提示词可以要求模型这样做，但程序没有因此自动完成事实核验。当前代码的 `COMPLETED` 只表示产生了非空候选回答，仍需要对照报告检查。

## 2、把零散要求写成处理流程

### 2.1 从禁令转向条件与动作

「不要编造」「务必准确」说明了不能发生什么，却没有告诉模型信息不足时下一步应该做什么。天气问题中的缺口至少有三种：缺少用户条件、缺少工具结果、服务返回了未知值。

这三种情况需要不同处理。没有城市时追问；服务失败时说明本次未取得信息；某个字段为 null 时只把该字段视为未知，不能把整份天气结果都判为不可用。

[WeatherPrompts.java](weather-agent/src/main/java/example/weather/WeatherPrompts.java) 的 rules 模式把处理方法组织成以下顺序：

```text
确认城市与日期
    → 搜索候选地点，核对地区
    → 使用实际返回的地点 ID 查询天气
    → 将目标日期与预报日期对应起来
    → 区分查到的事实、出行建议和未知项
    → 写明来源并结束，或说明还缺什么
```

这里的顺序存在数据依赖：第二个工具需要使用第一个工具返回的地点 ID。但「城市不明确」是一个可以提前结束并追问的分支，并不要求模型带着缺失参数把整条流程跑完。

### 2.2 完成条件影响工具调用

如果提示词只说「查询天气」，模型取得任意一份天气结果后就可能停止。用户实际还要求明天、概率和来源，因此完成条件需要覆盖这些要求。

反过来，提示词也不应要求「至少查询三次再回答」。已经取得足够依据时，多次重复请求会增加成本，还可能引入更新时间不同的数据。判断下一步应围绕信息缺口，而不是动作数量。

本例的程序预算独立存在：最多 8 次模型调用、12 个工具请求。模型不能通过改变回答措辞扩展预算。流程帮助选择动作，Java 负责限制实际执行。

### 2.3 指令之间也会发生冲突

「任何问题都立即回答」与「地点不明先追问」可能冲突；「不要遗漏信息」与「只用一句话回答」也可能冲突。堆叠更多要求不一定改善结果，可能只是把取舍留给模型。

这时应写清优先处理的条件。例如先保证地点和日期正确，再尽量简洁；缺少必要信息时，允许本轮只提出一个具体问题。不要同时要求模型给出完整预报和承认没有预报数据。

## 3、工具说明也是提示词的一部分

### 3.1 模型需要知道工具能证明什么

天气工具的契约见 [WeatherTools.java](weather-agent/src/main/java/example/weather/WeatherTools.java)：

| 工具 | 输入 | 返回及边界 |
|---|---|---|
| `searchLocations` | 城市名称 | 最多五个候选及其 ID、地区、坐标和时区，不直接返回天气 |
| `getWeather` | 本次已检索到的地点 ID | 当前条件与包含今天的三天预报，保留有效时间、单位和来源 |

如果只告诉模型 `getWeather` 的名字，它未必知道参数需要的是地点 ID，也未必知道这个 ID 必须先从搜索中获得。说明中的前置条件，会影响模型能否组装出可以执行的请求。

候选地点也不能只留下一个名字。城市搜索确实可能返回同名地点，行政区与国家帮助模型判断是否与用户要求相符。当前工具保留候选，由模型结合用户信息选择；无法确定时需要追问。

### 3.2 描述与执行必须一致

工具说明写着「查询未来三天」，程序就不能悄悄把所有日期都映射到今天。说明要求先搜索地点，执行层也应拒绝未检索过的 ID。

本例没有让模型传任意 URL 或坐标。`getWeather` 根据本次登记的候选构造固定服务地址。模型生成的参数仍然在 Java 中检查；工具名称、参数结构和调用预算会在整批执行前检查。

因此，工具说明与参数校验是两层工作。说明让模型理解契约，校验负责在它没有遵守契约时阻止执行。不能因为提示词写了「不得越权」，就开放不受限的文件、网络或命令工具。

### 3.3 单位和时间决定一句话的含义

「现在 18 度」与「明天最高 18 度」即使数值相同，含义也不同。当前条件、逐日最高最低温、时区和日期需要一起读取，不能只提取一个温度数字。

Open-Meteo 的 current 基于气象模型数据，daily 是逐日预报；它们不能被描述为本程序做出的现场测量。`retrievedAt` 是程序获取数据的时间，天气的有效时间仍看服务返回。官方字段说明见[天气 API](https://open-meteo.com/en/docs)。

## 4、示例和输出格式怎样帮助模型

### 4.1 示例应教会一种处理方式

下面是 examples 模式中的一种示例：

```text
用户：明天出门需要带伞吗？
助手：请补充要查询的城市。
```

这个示例教的是必要信息缺失时先追问，没有提供一份可以被误用的天气。另两个示例演示服务失败与 null 概率的处理。

Few-shot 示例适合补充抽象规则难以表达的行为，但需要与规则一致。若示例为了简洁省略来源，而规则要求注明来源，模型看到的指导就出现了矛盾。示例越多，还越需要检查它们是否覆盖了不同情况，还是重复同一种成功回答。

本例的 examples 是 rules 加上这些示例。这个设计便于观察新增指导的作用；它不保证比 rules 更好。真实效果必须通过任务与结果判断。

### 4.2 格式约束不是事实约束

要求按「城市和日期、天气信息、建议与不确定性、来源」输出，能让读者更容易检查答案。但顺序正确的回答仍可能引用错误城市，合法 JSON 里也可以装入错误温度。

天气项目当前返回自然语言候选答案，没有实现结构化回答 Schema、字段级事实比对或自动评分。若后续需要机器消费答案，应进一步确定响应结构、解析失败处理和事实检查；不能把提示词中的「请输出 JSON」写成代码已经保证结构化输出。

### 4.3 解释依据，不要求展示内部推理

教学中需要观察的是模型请求了什么工具、取得了什么结果、哪条结果支持候选回答，以及为什么继续或停止。这些都有可记录的外部证据。

可以要求回答给出简短依据，但不把一段很长的自述当作正确性的证明，也不以展示内部思考链作为本篇的验收条件。工具轨迹与原始结果才是检查行为的起点。

## 5、三种提示词怎样落到 Java

三个版本都由 `WeatherPrompts.of(mode)` 返回。每次任务开始时选定一个版本，运行中不动态改写系统规则：

```java
var context = new WeatherContext(
        WeatherPrompts.of(promptMode), question, contextMode);
var callbacks = ToolCallbacks.from(tools);
var configured = model.getDefaultOptions();
var builder = configured instanceof OpenAiChatOptions openAi
        ? openAi.mutate() : OpenAiChatOptions.builder();
var options = builder.toolCallbacks(callbacks).build();
Prompt prompt = new Prompt(context.initial(), options);
```

这段代码来自 [WeatherAgent.java](weather-agent/src/main/java/example/weather/WeatherAgent.java)。提示词放进系统消息，用户问题保留为用户消息，工具定义由 options 提供。真实天气数值没有提前出现在系统提示词中。

这里从已配置的模型选项派生，再设置本次工具。当前 SDK 的新 Builder 带有默认模型值，直接重建选项可能覆盖配置文件中的模型和参数。是否保留了指定配置，应通过实际请求核对，不能只看 YAML 写了什么。

| 模式 | 改变什么 | 主要观察 |
|---|---|---|
| basic | 基本任务和共同事实边界 | 能否在较少流程指导下正确完成任务 |
| rules | 增加条件、步骤、完成条件与输出顺序 | 是否更准确地定位缺口和选择下一步 |
| examples | 在 rules 上增加三类处理示例 | 是否更好地处理追问、失败和未知值 |

三个版本的天气工具、任务预算和上下文机制相同。温度参数等模型配置也应保持一致。把 temperature 设为 0 不能保证事实正确，也不意味着所有服务会给出逐字相同的结果。

## 6、先预测，再运行与核对

按[运行说明](weather-agent/README.md)完成天气连通检查与模型配置，然后运行：

```powershell
java '-Dfile.encoding=UTF-8' -jar target/weather-agent-0.0.1-SNAPSHOT.jar '--ask=北京市明天的天气怎样？请说明降水概率，并给出带伞建议、目标日期和来源。' --prompt=basic --context=full
```

下一次只把 basic 改为 rules，再按需要运行 examples。每次都是显式模型调用，会产生模型用量，不必一次运行所有组合。

运行前写下预测，运行后打开终端给出的报告。沿 `rounds` 看模型实际收到的消息，再沿 `toolEvents` 核对城市、天气字段和日期。最后对照候选答案，判断它是完整回答、合理追问，还是没有依据的猜测。

### 6.1 先用少量问题暴露不同缺口

| 问题 | 核对重点 |
|---|---|
| 北京市明天天气怎样，请给出日期和来源 | 地点、目标日期与来源是否匹配 |
| 明天需要带伞吗 | 没有地点时是否追问，而不是猜测所在城市 |
| 比较北京市和上海市明天的天气 | 两个地点的结果是否分别取得，日期是否一致 |
| 查询一个超出返回三天范围的日期 | 是否说明当前工具没有该日预报 |

服务限流、网络不可用、null 字段等情况适合用可控替身检查程序处理。不要为了制造失败而频繁请求真实服务。本机替身的结论与真实模型实验分开记录。

### 6.2 真正的对照比「换一个提示词」严格

两次调用之间，天气可能更新，模型也可能选择不同路径。即使 rules 的回答这次更完整，也只能先记录这次观察，不能立刻断言它提升了某个百分比的成功率。

要研究提示词的稳定效果，需要固定任务集、模型与参数，记录全部运行和实际天气快照，预先定义评分条件。严格固定工具观察的重复评估还需要专门的回放设计，当前命令行项目尚未提供。参考书的[提示工程消融实验](https://bojieli.github.io/ai-agent-book/chapter2/prompt-engineering/)可用于进一步理解控制变量和逐轮定位的做法。

## 7、从提示词走向上下文

提示词写清楚后，问题仍可能出现：工具查到了天气，但下一轮没有带上；模型忘了最初问的是明天；历史里同时留下多份旧预报；压缩后只剩温度，没有日期和单位。

这些问题需要检查每轮的全部输入。下一篇[《上下文工程》](04-context-engineering.md)继续使用天气助手，研究事实怎样进入请求、状态怎样更新，以及缩短输入时怎样保留决策所需的信息。

本篇实现了可选择的提示词与报告入口，并通过本机协议检查；尚未完成真实模型质量对照。因此本文不把任何提示词版本描述为已被实验证明更优。
