# Javaer 转 Agent：从第一个例子到工程实践

这份计划面向会写 Java、了解 Spring 和基本接口调用、希望逐步掌握 Agent 开发的读者。学习围绕一个项目展开：**做一个项目资料助手，能够查找文档、根据反馈继续获取依据，最后给出可核对的回答。**

先体验模型在不同输入条件下的表现，再理解工具循环；看懂手写实现后交给框架管理，随后加入多轮对话。遇到信息、状态和运行方面的问题，再学习检索、记忆、协议与编排，最终完成一个能交付、能验证的原型。

第 02 篇的 `first-agent` 示例提供两份固定、公开的教学文档，以及 `searchDocs`、`readDoc` 两个只读工具。程序使用 Spring AI 的模型与工具组件，由应用代码控制循环；每次 HTTP 请求重新建立消息和轨迹，没有跨请求会话记忆，也没有真实业务资料的用户权限隔离。

### 学习路线总览

| 阶段 | 核心问题 | 本阶段成果 |
|---|---|---|
| 0：观察模型调用 | 模型实际看到了什么，答案依据从哪里来 | 同一个问题在不同输入条件下的对照记录 |
| 1：建立 Agent 概念 | 下一步由程序预先安排，还是由模型根据反馈选择 | 对问答、Workflow、Agent 的解释与场景判断 |
| 2：理解并实现工具循环 | 工具怎样执行，反馈怎样返回，任务怎样停止 | 可解释的 Java 工具循环及成功、失败轨迹 |
| 3：框架托管与多轮对话 | 框架代管什么，连续提问需要保存什么 | 框架版资料助手、会话隔离与追问继续实验 |
| 4：按问题扩展能力 | 缺资料、上下文过长、跨会话记忆分别怎么解决 | 一项能力的改动前后对照 |
| 5：评测与项目交付 | 怎样确认任务完成，怎样让他人使用 | 可重复验收的原型、说明与已知限制 |
| 6：Harness 与工程改进 | 怎样让执行过程可观察、可恢复、可维护 | 一条源码执行链分析和一次经过验证的改进 |

阶段 0～3 构成基础主线。阶段 4 根据实际问题选学，不要求学完所有分支才能进入阶段 5；阶段 6 带着自己的工程问题研究实现。验证从第一次练习就开始，阶段 5 再将零散用例整理成完整验收。

初学者按阶段推进；已经会调用模型，可以用阶段 0 的实验检查理解；已经能解释工具循环，可以通过阶段 2 的验收后进入阶段 3。需要先体验框架原型的读者，也可以在阶段 0、1 后先跑一个官方工具示例，再回到阶段 2 理解控制过程。

这里按学习成果推进，不预设完成天数。模型训练、完整 Python 技术栈和多个框架的横向比较按需后置。

### 每次学习都完成一次小实验

> 明确问题 → 写下预测 → 运行基线 → 改变一个主要因素 → 对照轨迹 → 记录结论。

同一轮对照尽量保持问题、文档、模型和配置一致。例如研究工具反馈时，就不要同时更换模型或搜索实现。记录全部尝试，结果不符合预测时，先检查输入和轨迹，再决定如何调整。

引导预览只能说明程序准备发送什么；模拟服务检查能验证程序处理约定响应的行为；真实模型运行才能观察该次模型的实际选择。三类证据分开记录。一次成功不代表所有输入都可靠，模型自述完成也需要文档和执行结果支持。

## 3、阶段 0～2：从输入对照到工具循环

### 阶段 0：观察模型调用，找出回答依据

**要解决的问题：模型知道哪些项目事实，规则、资料和工具分别改变了什么？**

先读[概念篇](01-what-is-agent.md)中模型、上下文和工具的说明，再跟随[第一个 Java Agent](02-first-java-agent.md)运行 `--guided`。需要补课时选读 Hello-Agents 的模型基础，以及李博杰第一章的上下文实验。

沿用现有问题：“订单查询的分页参数怎么传？请给出文档依据。”比较四种配置：

| 引导配置 | 提供给模型什么 | 观察什么 |
|---|---|---|
| 0：只有问题 | 用户问题 | 没有项目资料时，答案是否有可核对的依据 |
| 1：增加规则 | 问题和回答要求 | 能否说明资料不足；规则没有新增项目事实 |
| 2：直接提供文档 | 问题、规则与两份文档正文 | 能否依据正文回答，并指出未规定的信息 |
| 3：提供工具 | 问题、规则与工具定义 | 需要哪些工具结果，才能得到正文依据 |

**这里的引导配置 0～3 是同一次练习的对照编号，不对应本文学习阶段 0～3。** 本阶段先观察，配置 3 的执行细节在学习阶段 2 拆开。

先写预测再选择实际运行；只看预览可以跳过调用。实际调用需要按运行说明配置模型服务，并产生相应调用用量。当前两份文档已经包含“正文引用另一份资料”和“默认值未规定”两种条件，初次实验无需新增材料。

**验收与产出：** 保存输入条件和实际回答，能指出答案依据，解释“增加回答规则”和“增加事实材料”的区别。直接将文档放入请求的配置没有检索过程，不把它记作已经完成 RAG。

**进入下一阶段：** 能回答模型看到了什么，再分析它是否参与决定下一步。

### 阶段 1：建立概念，判断由谁选择下一步

**要解决的问题：什么时候一次问答或固定流程就够了，什么时候需要根据反馈调整行动？**

主读 Hello-Agents 的“初识智能体”与“智能体经典范式构建”中的 ReAct 部分，对照[概念篇](01-what-is-agent.md)的资料助手。资料篇中程序员 Left、川处安的文章可用于换一种表述复习，不需要重复通读全部入门材料。

用同一个问题推演三种过程：直接粘贴正文后回答；程序固定搜索、读取、回答；模型读到公共约定的引用后决定继续读取。标出每一步由代码安排还是模型选择，并用已有轨迹检查推演。

固定工作流也可以包含分支、重试和工具调用；多次调用模型也不能单独作为 Agent 的判断依据。关注反馈是否参与后续行动选择，并说明当前任务为什么采用某种方式。

**验收与产出：** 不看资料解释三种方式的区别，写出资料助手的一次执行过程，并指出程序与模型各自承担的职责。

**进入下一阶段：** 已经能描述过程，再沿着 Java 实现核对它如何发生。

### 阶段 2：理解并实现工具循环

**要解决的问题：模型只返回工具请求时，Java 怎样执行、回填结果并决定继续或停止？**

主读 Learn Claude Code 的循环、工具、权限章节。当前根目录主线对应 `s01`、`s02`、`s03`，不要与旧版 `docs/`、`agents/` 的编号混用。对照 Spring AI 工具文档中应用控制执行的部分，以及本地 [DocAgent](first-agent/src/main/java/example/agent/service/DocAgent.java) 和 [DocTools](first-agent/src/main/java/example/agent/tool/DocTools.java)。

从已有示例追踪这条链，再尝试自己补写或复现关键步骤：

> 构造消息和工具定义 → 调用模型 → 识别工具请求 → 校验并执行 → 按调用 ID 回填结果 → 再次调用模型 → 回答或停止。

| 当前工具 | 已有行为 | 学习时核对什么 |
|---|---|---|
| `searchDocs` | 按标题包含关系搜索，返回 ID 与标题 | 参数是否合法、是否命中、搜索结果是否足以支持回答 |
| `readDoc` | 按固定集合中的文档 ID 返回来源和正文 | ID 是否有效、文档是否存在、正文怎样进入下一轮 |

先分析一次成功运行，再观察非法参数、文档缺失、重复请求或预算耗尽时的处理。程序已有工具名单、参数和预算等限制；固定公开文档不等于实现了用户授权，真实资料权限是后续扩展任务。

理解基线后，补做两类对照：移除工具定义，观察能否取得项目依据；保留合法的工具返回结构，但返回“未取得正文”，观察模型怎样继续或停止。工具反馈实验需要另行实现，不能把缺失必要协议消息造成的接口错误当作模型行为结论。

记录工具是否实际执行、结果是什么、模型下一轮收到什么。不要预设必须按固定顺序搜索，也不要以答案恰好正确替代读取依据的记录。理解循环后，可以选做“先列检索计划”或“回答后检查引用”，观察是否改善结果，并保留调用预算。

**验收与产出：** 能逐轮解释成功与失败各一次；能定位模型调用、工具分发、结果回填和停止代码；用文档核对候选答案。保留两条轨迹与对应解释。

**进入下一阶段：** 先能解释已有循环，再观察框架替你承担了哪些工作。

## 4、阶段 3：框架托管与多轮对话

**要解决的问题：怎样从一次独立任务，走向可以连续交流的资料助手？**

主读 [Spring AI Tool Calling](https://docs.spring.io/spring-ai/reference/api/tools.html)、[Chat Memory](https://docs.spring.io/spring-ai/reference/api/chat-memory.html)，配合官方示例。资料篇 B02 的 Spring AI 视频课程可用于跟练，接口和行为与项目所用版本核对。

这一阶段分步推进。迁移时先保留两份文档、工具业务实现和原有检查用例，再逐步改变消息管理方式。

| 步骤 | 学习与实验 | 验收要求 |
|---|---|---|
| 3A：框架接管工具循环 | 使用 `ChatClient` 及所用版本支持的执行机制，替换应用手写循环 | 原有用例通过；能定位工具执行、结果回填、异常与预算控制的位置 |
| 3B：连续追问 | 依次问“分页参数怎么传？”和“那它的默认值呢？”，比较不带历史与带历史 | 能解释第二轮的指代依据；默认值仍以实际文档为准 |
| 3C：会话隔离 | 引入会话 ID，在两个会话中交替提问 | 同一会话能延续上下文，不同会话不混用消息 |
| 3D：追问后继续 | 扩展缺少版本信息的教学任务，用户补充后继续回答 | 待解决问题与补充信息能正确关联，不能确定时不猜测 |
| 3E：检查恢复边界 | 重启后观察对话与任务状态；需要重启恢复时再实现持久化 | 准确说明保存了什么、丢失了什么，以实际恢复结果为依据 |

3D 的版本材料属于练习扩展，具体内容应先定义并记录，再用于对照，不把它描述为现有示例已有第三份文档。

分别理解三类信息：**一次任务内部的工具历史、用户多轮对话历史、恢复未完成任务所需的状态。** 检查所选记忆组件和存储是否保存中间工具消息；接入会话存储后，还要实际验证它能恢复到什么程度。会话 ID 也不能替代可信用户身份和访问授权。

**验收与产出：** 留下框架迁移前后对照，以及连续追问、会话隔离、补充信息后继续的记录。能够说明哪些工作交给框架、哪些仍由业务代码负责；恢复能力按实际实现标注。

**进入下一阶段：** 根据已经观察到的问题选择扩展主题；若当前功能足够完成约定任务，也可以先进入阶段 5 整理交付。

## 5、阶段 4：按问题补齐信息与状态

**要解决的问题：当前助手具体缺什么，哪项能力能够解决它？**

先写下失败输入和当前结果，再选择一个主题。下表资源来自资料篇，按名称查找阅读入口；每项扩展继续使用资料助手，保留原有检查用例。

| 遇到的问题 | 学什么、从哪里读 | 配套实验与完成条件 |
|---|---|---|
| 文档增加，关键词搜索找不准 | Hello-Agents“记忆与检索”、资料篇 G17 All-in-RAG、[本仓库 RAG 笔记](../../rag/README.md) | 用相同问题比较检索命中与答案依据，分别定位检索错误和生成错误 |
| 对话变长，旧资料干扰判断 | Hello-Agents“上下文工程”、Learn Claude Code 上下文压缩章节 | 比较压缩前后，检查约束、证据、未完成事项是否保留 |
| 跨会话需要延续获准保存的信息 | Learn Claude Code 记忆章节、资料篇第 8.3 节 Learn Agent Memory | 用少量数据验证保存、召回、更新、删除与用户隔离 |
| 相同工具需要被不同客户端使用 | 资料篇 D06 MCP 官方介绍、G15 MCP Java SDK | 将同一个只读工具接成服务，验证返回结果、权限与连接失败 |
| 同类任务反复使用相同步骤 | 资料篇第 8.2 节 Agent Skills 标准与编写指南 | 整理版本核对、引用检查指引，用相同任务比较遗漏情况 |
| 流程需要分支、暂停与重启恢复 | 资料篇第 8.1 节编排文章；Spring AI Alibaba 或 LangGraph4j 中选择适用实现 | 让任务中断后恢复，检查状态完整性和是否重复执行 |
| 一个任务需要独立分工 | 资料篇中的单 Agent 到协作主题与综合项目 | 拆出一个职责明确的子任务，与单 Agent 比较质量、耗时和协调成本 |

学习依赖是：先看清工具反馈，再讨论规划调整；先分清会话与任务状态，再做长期记忆；先检查每轮输入，再做压缩；先能验证单 Agent，再比较多 Agent。模型自评或另一个 Agent 的结论也要用实际资料和结果核对。

**验收与产出：** 说明原问题、新增能力和改动后结果，保留相同输入下的前后对照。没有改善时记录原因，不以接入工具或框架数量作为学习成果。

## 6、贯穿各阶段的验证，以及阶段 5 的项目交付

### 从第一条用例开始验证

先读资料篇 D01 评测文章，理解任务、轨迹和判定标准。需要进一步补充时，再读 Hello-Agents 或李博杰书中的评估主题；已有失败案例可参考资料篇第 8.4 节 EvalGrill 的入口，整理为可重复执行的用例。

| 条件 | 应该检查什么 | 何时加入 |
|---|---|---|
| 文档直接给出参数 | 答案准确，引用支持结论 | 阶段 0 提供正文后 |
| 接口引用另一份约定 | 工具版实际取得相关正文后回答 | 阶段 2 起 |
| 询问未写明的默认值 | 明确说明没有依据 | 阶段 0 起 |
| 非法参数、文档缺失或预算耗尽 | 返回可解释结果，必要时受控停止 | 阶段 2 起 |
| 文档夹带与任务无关的执行指令 | 不把资料中的指令当作用户授权 | 构造对应教学材料后 |
| 新旧版本或版本信息不足 | 根据适用条件回答，不能判断时追问 | 扩展版本材料后 |
| 两个会话交替提问 | 历史与待解决问题不串用 | 阶段 3 实现会话后 |
| 当前用户无权读取资料 | 执行入口拒绝访问，无其他路径绕过 | 实现可信身份与文档权限后 |
| 中断并重启 | 状态恢复符合约定，不重复执行已完成动作 | 实现持久化恢复后 |

当前示例的 `COMPLETED` 表示产生了候选答案，仍需核对正文与轨迹；HTTP 成功、代码编译通过或模型说“已完成”，都不能单独证明任务成功。

同一问题可以重复执行，记录所有成功和失败，并注明运行次数、模型与工具调用次数、耗时和可取得的用量。没有取得的统计写明未知，不用估算值冒充实测。

排查时先定位：资料没搜到，检查检索；取得资料却没进入请求，检查上下文；依据齐全仍回答错误，检查输出；动作重复，检查循环和状态。一次只调整一个主要因素，再跑相同用例。

### 阶段 5：让他人能够使用并验收

**要解决的问题：离开开发者现场解释，别人能否完成约定任务并理解失败？**

沿用已有入口，整理配置、启动、提问、来源查看和失败处理说明。需要对真实用户开放资料时，再落实身份、权限、数据隔离及运行限制，并补上相应验收。若以后加入写操作，还需校验业务状态、幂等和失败补偿；超时后先确认执行结果，再决定是否重试。

| 交付物 | 要说明的内容 |
|---|---|
| 可运行原型 | 当前支持什么任务、使用什么入口、有哪些限制 |
| 使用说明 | 环境与版本、配置方式、启动方法、失败后如何继续 |
| 验收记录 | 输入、预期、实际结果、引用依据、未解决问题 |
| 执行记录 | 一次任务关联的模型与工具调用、耗时和停止原因，敏感内容脱敏 |

**验收与产出：** 由未参与开发的人按说明完成约定任务，检查正常和失败条件，留下结果。原型通过仅证明已验证范围，生产部署的容量、监控和运维要求继续按实际环境补充。

## 7、阶段 6：带着问题研究 Harness 与工程化

**要解决的问题：自己的实现遇到了什么限制，可以从其他系统借鉴哪项机制？**

Harness 的基本认识在阶段 2 就开始：构造上下文、协调工具执行和控制循环都属于围绕模型运行的工作。本阶段进一步研究状态、恢复、验证与观测的设计。

先读 Learn Agent Architecture 中对应主题，再选择一个项目追踪一条执行链：

| 阅读入口 | 适合研究的问题 |
|---|---|
| [AgentScope Java](../agentscope/README.md) | Java 中怎样组织 Agent、工具和会话；资料篇 G13、B06 可配合阅读 |
| [Pi Agent](../pi-agent/README.md) | 循环、会话和上下文压缩如何分工；对应资料篇 G20 |
| [DeepSeek Harness](../deepseek-harness/README.md) | 运行能力如何组织，状态和扩展机制如何衔接；配合资料篇第 8.3 节 |
| 资料篇中的 DeerFlow | 一次检索与报告任务怎样拆分和汇总 |
| 资料篇中的 mini-swe-agent、OpenHands | 编码任务怎样执行、验证与停止 |
| 资料篇中的 Browser Use | 浏览器操作怎样观察、行动和验证结果 |

记录所读 commit/tag，沿“输入 → 构造上下文 → 调用模型 → 分发工具 → 回填结果 → 停止”定位代码。第一遍能解释正常和失败各一条路径即可；只读过的部分标为源码分析，实际执行过的部分保留输入与结果。

需要定位耗时时，再查资料篇第 8.4 节的 OpenTelemetry 与 AI 调用记录资料。回到自己的助手，只迁入一项能解决当前问题的改进，用原有用例复测，再比较质量、调用次数、耗时或人工介入情况。

**验收与产出：** 一份有代码依据的执行链分析，以及一项有运行证据的改进。能够解释它解决了什么、增加了什么成本、仍有什么限制。

## 8、现在怎样继续，以及如何记录进度

### 从当前示例衔接下一步

尚未运行示例时，先读运行说明，完成阶段 0 的预览与实际调用。已经运行过时，按下面的顺序检查掌握情况，通过后继续，不把已有文章视为个人完成记录。

| 顺序 | 阅读与行动 | 留下什么 |
|---|---|---|
| 1 | 对照李博杰第一章的实验思路，复盘已有四种引导配置 | 输入条件、预测与实际结果 |
| 2 | 对照 Learn Claude Code 的循环、工具与权限主题，解释 Java 执行链 | 成功、失败各一条轨迹及解释 |
| 3 | 阅读 Spring AI 工具文档，完成阶段 3A | 框架迁移前后对照与原用例结果 |
| 4 | 阅读 Chat Memory，逐项完成阶段 3B～3E | 追问、会话隔离、补充信息和恢复边界记录 |
| 5 | 用 D01 评测方法整理已有检查 | 可重复执行的验收集与待解决问题 |

能够解释第 02 篇的手写循环后，继续[第 03 篇：让 Spring AI 管理工具循环与多轮对话](03-spring-ai-conversation.md)。先对照框架托管，再检查会话能力，每次变化都用原有用例核对。第 03 篇已完成离线验证，个人学习与真实模型验收仍需分别记录。

### 每次学习的记录

| 记录项 | 要写什么 |
|---|---|
| 问题 | 这次要解释或解决什么，为什么现在需要它 |
| 依据 | 来源链接、章节、学习日期、代码与依赖版本 |
| 预测 | 改动前预计出现什么，依据是什么 |
| 实验 | 基线、改变的因素、输入、实际结果和关键轨迹 |
| 结论 | 已验证什么，哪些仍是推断，哪些用例未通过 |
| 下一步 | 根据本次结果，接着验证或实现什么 |

合上资料后，尝试讲清：模型看到了什么，工具实际做了什么，反馈怎样影响下一步，为什么停止，凭什么判断完成。讲不清的位置，就是下一次阅读和实验的起点。
