# Javaer 转 Agent：从第一个例子到工程实践

本系列面向会写 Java、了解 Spring 和基本接口调用的开发者。先理解 Agent 并运行一个工具循环，再逐步研究提示词、上下文、记忆、工具、运行时和工程验证。

学习范围与递进方向参考 [AI Agent Guide](https://github.com/fuzhengwei/ai-agent-guide)，机制讲解和对照实验参考[《深入理解 AI Agent》](https://bojieli.github.io/ai-agent-book/astro/)。前者帮助安排能力主题，后者帮助把问题讲透；具体 Java 行为以本地实现与实际运行记录为准，不再按参考书章号给本系列机械编号。

## 2、把每篇写成一个能够解释的问题

行文从读者遇到的现象开始，解释现象背后的机制，再沿 Java 代码追踪信息与控制流。实验用于检查解释是否成立；结尾说明适用条件、失败方式和下一步问题。概念介绍、代码运行手册、实验记录各自承担不同任务，避免反复堆叠术语。

| 篇目 | 核心问题 | 读完应能说明什么 |
|---|---|---|
| 02 | 模型怎样请求 Java 工具 | 请求、执行和结果回填分别发生在哪里 |
| 03 | 同样的工具，为什么任务说明影响处理方式 | 角色、流程、示例与事实来源分别解决什么问题 |
| 04 | 规则没有变，为什么下一轮仍会答错 | 应用保存了什么、模型本轮收到了什么、哪些信息被遗漏或压缩 |
| 05 | 下次任务应该继续使用哪些信息 | 用户记忆与知识资料怎样提取、检索、更新和删除 |

深度体现为能够解释取舍。例如天气工具返回了温度，还需要区分当前条件与未来预报；上下文缩短了，还要核对是否保留目标日期、时区、单位、来源和失败。代码运行成功只能证明已检查的路径，不能代替这些解释。

## 3、提示词与上下文分别怎样实践

先运行天气项目的 --weather-check，确认真实城市与天气接口能访问，再配置模型运行天气问题。完整命令见[项目说明](weather-agent/README.md)。

提示词篇使用同一个问题、工具集合和上下文策略，对照 basic、rules、examples。观察地点缺失时是否追问、天气失败时是否说明缺口、建议是否与返回依据一致。三种模式共享事实与权限边界，改变的是处理流程和示例。

提示词篇另有两个无需密钥的 [Java 小实验](prompt-labs/README.md)：用人工 logits 解释温度与 top-p，用合成观察解释字段核验。22 项自检验证计算与核验逻辑，不代表真实模型通过了质量评估。三种累计提示词模式属于方案对照，严格的单因素消融需另行控制变化范围。

上下文篇固定提示词，对照 full、state、compact。逐轮检查消息，解释工具结果怎样进入下一次请求；再检查状态更新与完整批次压缩。短任务没有触发压缩是正常结果，不为了显示压缩效果诱导模型无意义地重复查天气。

真实天气会变化。每次记录实际返回、有效时间、获取时间、模型配置和问题，不能把不同日期、不同数据源的两次回答当作严格控制变量的实验。固定替身只用于本机协议检查，并在记录中明确标注；正式天气入口不会在失败时回退到编造的数据。

## 4、后续按能力逐步展开

以下是主题规划，不表示已经形成文章或实现。具体拆篇与编号在开展对应主题时确定。

| 方向 | 要研究的问题 | Java 实践与验收方向 |
|---|---|---|
| 决策与运行时 | ReAct、意图识别、行动选择、循环与停止 | 解释正常和失败轨迹；识别模型决策与程序约束 |
| Harness | 上下文、工具、预算、状态、恢复怎样共同支撑任务 | 沿同一任务追踪执行边界，再增加一项经过验证的能力 |
| 工具设计 | 参数、描述、结果、错误、超时与副作用 | 建立正常、无结果、非法参数和失败的工具契约 |
| MCP 与 Skills | 跨客户端调用和工作方法复用分别解决什么问题 | 工具接口与指导内容分别接入；不把加载指导当成授权 |
| 知识检索 | 分块、召回、重排、来源、版本与知识更新 | 从第 05 篇继续，分别检查检索和生成的失败 |
| CLI 与 Coding Agent | 文件、命令、代码修改与环境反馈 | 在明确范围中执行并用差异、编译和针对性检查验收 |
| 协作与编排 | 状态机、检查点、中断恢复和多 Agent 交接 | 比较单 Agent 基线与协作成本，检查重复执行和信息丢失 |
| 框架与平台 | Spring AI、其他框架与可视化平台如何取舍 | 用同一任务比较控制能力，不为展示框架重新造业务 |
| GUI 与综合实践 | 新的观察和动作接口怎样参与循环 | 记录动作前后的环境证据与成功条件 |
| 工程化 | 评估、可观测性、安全、部署与模型服务 | 固定任务集、追踪故障、核对成本与权限，再讨论部署条件 |

原路线中的模型后训练与持续进化保留为进阶方向：先有可重复的评估与失败样本，再讨论训练数据、模型参数更新和迭代机制。提示词修改不算模型后训练。

## 6、怎样记录学习结果

每项实验保留问题、预测、实际输入、工具返回、候选答案和未解决事项。研究某项机制时只改变主要因素；结果不符合预测时，先查实际轨迹，再修改规则或代码。

本系列区分四类证据：主代码编译、使用替身的本机协议检查、真实外部工具接入、真实模型质量评估。前三项不能自动推出第四项通过。报告中的 COMPLETED 仅表示得到候选回答，答案仍需核对。

当前天气项目已完成编译、打包、41 项本机断言以及 Java 程序对真实 Open-Meteo 的连通检查；尚未完成真实模型质量评估。第 05 篇中的长期记忆与新检索策略仍按正文标记的范围逐步实现。
