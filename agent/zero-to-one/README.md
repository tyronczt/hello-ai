# Javaer 转 Agent：从第一个例子到工程实践

这份计划面向会写 Java、了解 Spring 和基本接口调用、希望逐步掌握 Agent 开发的读者。实践从一个项目资料助手开始：查找文档、根据反馈继续获取依据，最后给出可核对的回答。

学习顺序以[《深入理解 AI Agent》全书目录](https://bojieli.github.io/ai-agent-book/astro/#contents)为主线。保留现有 01～04 篇，05～11 篇先列为规划；后续围绕 Java 实践，逐步扩展工具、执行环境、评估与协作能力。

### 每次学习都完成一次小实验

> 明确问题 → 写下预测 → 运行基线 → 改变一个主要因素 → 对照轨迹 → 记录结论。

同一轮对照尽量保持问题、文档、模型和配置一致。例如研究工具反馈时，就不要同时更换模型或搜索实现。记录全部尝试，结果不符合预测时，先检查输入和轨迹，再决定如何调整。

引导预览只能说明程序准备发送什么；模拟服务检查能验证程序处理约定响应的行为；真实模型运行才能观察该次模型的实际选择。三类证据分开记录。一次成功不代表所有输入都可靠，模型自述完成也需要文档和执行结果支持。

## 3、01～02：从入门认识到第一个 Java Agent

### 先观察输入，找出回答依据

**要解决的问题：模型知道哪些项目事实，规则、资料和工具分别改变了什么？**

先读[概念篇](01-what-is-agent.md)中模型、上下文和工具的说明，再跟随[第一个 Java Agent](02-first-java-agent.md)运行 `--guided`。需要补课时选读 Hello-Agents 的模型基础，以及李博杰第一章的上下文实验。

沿用现有问题：“订单查询的分页参数怎么传？请给出文档依据。”比较四种配置：

| 引导配置 | 提供给模型什么 | 观察什么 |
|---|---|---|
| 0：只有问题 | 用户问题 | 没有项目资料时，答案是否有可核对的依据 |
| 1：增加规则 | 问题和回答要求 | 能否说明资料不足；规则没有新增项目事实 |
| 2：直接提供文档 | 问题、规则与两份文档正文 | 能否依据正文回答，并指出未规定的信息 |
| 3：提供工具 | 问题、规则与工具定义 | 需要哪些工具结果，才能得到正文依据 |

**引导配置 0～3 是第 02 篇同一次练习的对照编号，与本系列篇号无对应关系。** 先观察不同输入的影响，再拆解配置 3 的工具循环。

先写预测再选择实际运行；只看预览可以跳过调用。实际调用需要按运行说明配置模型服务，并产生相应调用用量。当前两份文档已经包含“正文引用另一份资料”和“默认值未规定”两种条件，初次实验无需新增材料。

**验收与产出：** 保存输入条件和实际回答，能指出答案依据，解释“增加回答规则”和“增加事实材料”的区别。直接将文档放入请求的配置没有检索过程，不把它记作已经完成 RAG。

**接着检查：** 能回答模型看到了什么，再分析它是否参与决定下一步。

### 对照概念，判断由谁选择下一步

**要解决的问题：什么时候一次问答或固定流程就够了，什么时候需要根据反馈调整行动？**

对照原书第一章与[概念篇](01-what-is-agent.md)的资料助手，判断每一步由谁选择。需要补课时，再读 Hello-Agents 的「初识智能体」与「智能体经典范式构建」中的 ReAct 部分；资料篇中程序员 Left、川处安的文章可用于换一种表述复习，不需要重复通读全部入门材料。

用同一个问题推演三种过程：直接粘贴正文后回答；程序固定搜索、读取、回答；模型读到公共约定的引用后决定继续读取。标出每一步由代码安排还是模型选择，并用已有轨迹检查推演。

固定工作流也可以包含分支、重试和工具调用；多次调用模型也不能单独作为 Agent 的判断依据。关注反馈是否参与后续行动选择，并说明当前任务为什么采用某种方式。

**验收与产出：** 不看资料解释三种方式的区别，写出资料助手的一次执行过程，并指出程序与模型各自承担的职责。

**接着检查：** 已经能描述过程，再沿着 Java 实现核对它如何发生。

### 沿着 Java 代码理解工具循环

**要解决的问题：模型只返回工具请求时，Java 怎样执行、回填结果并决定继续或停止？**

沿第 02 篇与本地 [DocAgent](first-agent/src/main/java/example/agent/service/DocAgent.java)、[DocTools](first-agent/src/main/java/example/agent/tool/DocTools.java) 理解工具循环，结合 Spring AI 工具文档中应用控制执行的部分核对。需要小型实现对照时，再读 Learn Claude Code 的循环、工具、权限章节；当前根目录主线对应 `s01`、`s02`、`s03`，不要与旧版 `docs/`、`agents/` 的编号混用。

从已有示例追踪这条链，再尝试自己补写或复现关键步骤：

> 构造消息和工具定义 → 调用模型 → 识别工具请求 → 校验并执行 → 按调用 ID 回填结果 → 再次调用模型 → 回答或停止。

| 当前工具 | 已有行为 | 学习时核对什么 |
|---|---|---|
| `searchDocs` | 按标题包含关系搜索，返回 ID 与标题 | 参数是否合法、是否命中、搜索结果是否足以支持回答 |
| `readDoc` | 按固定集合中的文档 ID 返回来源和正文 | ID 是否有效、文档是否存在、正文怎样进入下一轮 |

先分析一次成功运行，再观察非法参数、文档缺失、重复请求或预算耗尽时的处理。程序已有工具名单、参数和预算等限制；固定公开文档不等于实现了用户授权，真实资料权限是后续扩展任务。

理解基线后，补做两类对照：移除工具定义，观察能否取得项目依据；保留合法的工具返回结构，但返回“未取得正文”，观察模型怎样继续或停止。工具反馈实验需要另行实现，不能把缺失必要协议消息造成的接口错误当作模型行为结论。

记录工具是否实际执行、结果是什么、模型下一轮收到什么。不要预设必须按固定顺序搜索，也不要以答案恰好正确替代读取依据的记录。理解循环后，可以选做“先列检索计划”或“回答后检查引用”，观察是否改善结果，并保留调用预算。

**验收与产出：** 能逐轮解释成功与失败各一次；能定位模型调用、工具分发、结果回填和停止代码；用文档核对候选答案。保留两条轨迹与对应解释。

**衔接第 03 篇：** 先能解释已有循环，再逐轮检查模型收到的信息，进入上下文工程。

## 4、03：上下文工程

**要解决的问题：每轮模型调用需要什么信息，怎样组织这些信息并控制上下文长度？**

主读[第 03 篇：上下文工程](03-context-engineering.md)，对照《深入理解 AI Agent》第二章。继续使用 `first-agent` 的手写循环，先运行 `--context-lab`，再从报告解释每项策略；需要观察模型行为时，显式选择一种 `--context-live=<模式>`。

| 步骤 | 学习与实验 | 验收要求 |
|---|---|---|
| 03A：请求结构 | 对照 `report.json` 与 `wire-requests.json` | 能解释每轮新增的依据，区分 Java 视图与实际 HTTP 请求 |
| 03B：缓存布局 | 查看公共前缀实验与稳定系统规则；真实调用时再核对服务商用量 | 字符、Token 与缓存命中分别记录，缺失统计标为未取得 |
| 03C：提示词与工具说明 | 对照 `baseline`、`rules` 的流程表达 | 离线验证输入变化，真实调用再检查未知项与引用 |
| 03D：Skills 按需加载 | 比较 `eager` 与 `ondemand` 的首轮和后续输入 | 只加载请求过的指导，明确包内教学加载器的边界 |
| 03E：运行状态 | 检查 `state` 中由 Java 生成的执行状态 | 已读资料、失败和剩余预算准确，提醒与执行校验分开 |
| 03F：上下文压缩 | 用相同脚本比较 `state`、`compact` | 原始问题、来源、未知项和失败保留，工具批次完整配对 |

六种模式的完整离线实验目前包含 81 项断言；它验证本机协议、工具和上下文机制，不证明真实模型质量、Token 节省或缓存命中。更长资料、模型摘要和生产级上下文预算仍需扩展实验。

**验收与产出：** 一次逐轮上下文记录，以及一项已实现策略的前后对照。原始轨迹、示意消息和实测结果分别标明。

**衔接第 04 篇：** 能说明当前任务需要保留什么，再研究信息怎样跨会话保存与检索。

## 5、04：用户记忆与知识库

**要解决的问题：哪些信息值得跨会话保存，怎样取得适用且可核对的项目资料？**

主读[第 04 篇：用户记忆与知识库](04-user-memory-knowledge-base.md)，对照《深入理解 AI Agent》第三章。先区分会话历史、用户长期记忆、知识来源和可恢复任务状态，再选择存储与检索实现。

| 步骤 | 学习与实验 | 验收要求 |
|---|---|---|
| 04A：请求边界 | 核对 `first-agent` 的初始消息与本次工具历史 | 能指出新请求从哪里开始，哪些信息尚未跨请求保存 |
| 04B：记忆生命周期 | 用合成数据实现候选提取、保存、读取、修正和删除 | 主体、项目范围与来源准确，派生结果同步处理 |
| 04C：检索基线 | 观察标题搜索的命中与漏检，再选择一种新策略 | 分别检查检索、上下文输入和答案依据 |
| 04D：知识组织 | 准备有来源的长材料，保留章节、版本和引用关系 | 片段含义完整，引用可回读，适用范围正确 |
| 04E：更新与验证 | 更新或移除测试资料后重新查询 | 原文、索引和派生内容一致，不返回越权资料 |

记忆与检索可以按需补读 Hello-Agents、资料篇 G17 All-in-RAG、第 8.3 节 Learn Agent Memory 及[本仓库 RAG 笔记](../../rag/README.md)。新版本材料属于扩展实验，应先定义并记录，不能描述为现有示例已具备的资料。

**验收与产出：** 一组记忆生命周期记录，以及同一批问题上的检索与回答对照。新增能力以实际实现为准，原书统计不作为本项目结果。

**衔接第 05 篇：** 在记忆和检索中遇到的参数、返回结果、访问范围与失败问题，继续归入工具契约和执行机制研究。

## 6、05～11：后续篇目规划

以下各篇均为规划，先列学习目标、Java 实践方向与预期产出。具体案例和技术选型在对应实践启动时确定，按实现与验证结果逐步形成文章。

### 05：工具（规划）

从第 02 篇的 `searchDocs`、`readDoc` 出发，进一步研究工具描述、参数与返回结构、权限、超时、错误反馈和重试边界。需要跨客户端复用时，再研究 MCP 接入；具体协议实现按实际需求选择。

**Java 实践方向：** 为同一工具补齐正常、无结果、参数错误和执行失败的对照。若后续加入写操作，再验证幂等与副作用处理。计划产出一组工具契约、执行轨迹及对应检查。

### 06：Coding Agent 与通用 Agent（规划）

研究模型怎样通过读取代码、提出修改、执行命令和查看结果推进任务，以及代码作为工具时怎样扩展可执行的工作范围。沿着「观察环境 → 生成修改 → 执行 → 验证 → 继续或停止」理解反馈循环。

**Java 实践方向：** 在明确范围的测试项目中，选择一个小型 Java 修改任务，以文件差异、编译和针对性测试判断结果。运行权限与隔离方式在实现前确定。计划产出一次能够追溯修改、执行和验证过程的任务记录。

### 07：交互：观察与动作空间的扩展（规划）

研究文本之外的观察输入，以及界面操作等动作接口；进一步考虑长时任务的进度、暂停和恢复。语音、视觉、浏览器与界面交互作为候选方向，按具体任务选择一种开始。

**Java 实践方向：** 让 Java 应用接入选定的观察或动作接口，记录原始观察、模型请求、实际动作及动作后的结果。涉及任务恢复时，检查状态是否完整、已执行动作是否重复。计划产出一个交互样例及中断或失败处理记录。

### 08：Agent 的评估（规划）

把前几篇积累的正常与失败案例整理为固定任务集，明确答案、工具轨迹、任务完成情况和成本各自怎样判断。先建立单个系统的基线，再在相同任务与条件下比较改进。

**Java 实践方向：** 建立可重复运行的评估入口，保存输入、来源、执行轨迹、判定依据和实际用量。分别报告检索失败、上下文缺失、工具错误与回答错误。计划产出任务集、运行记录和对照报告；当前可先执行第 7 节的已有检查。

### 09：模型后训练（规划）

先理解监督微调、强化学习与 Agent 行为之间的关系，再区分上下文调整和模型参数更新。训练样本、反馈信号与评估问题分别整理，保留数据来源和划分依据。

**Java 实践方向：** 围绕已有工具任务整理样本与评估输入，由 Java 应用负责模型服务接入和结果记录。开展实际训练前，再确定模型、训练工具、数据与资源条件；取得实际训练产物后，才能进行训练前后对照。计划产出样本说明、评估设计及有条件开展的模型对照记录，提示词修改不能记作已完成后训练。

### 10：Agent 的持续进化（规划）

围绕真实执行中的失败建立改进过程：收集反馈、定位原因、提出候选修改、验证效果，再记录版本与回退方式。改进对象可以来自上下文、记忆、工具或执行策略，由失败证据确定。

**Java 实践方向：** 从已有助手中选取一类失败，每次只调整一项机制，用第 08 篇形成的任务集检查效果和退化。计划产出包含失败样例、修改依据、对照结果与版本记录的改进案例。

### 11：多 Agent 协作（规划）

在单 Agent 基线之上研究任务分工、输入输出约定、上下文交接、共享状态和失败传播。比较协作带来的效果与协调成本，再判断是否需要拆分。

**Java 实践方向：** 选择能够明确分工的任务，在相同资料与问题上对照单 Agent 和协作方案，记录质量、耗时、调用量和信息遗漏。共享状态与执行权限分别检查，其他 Agent 的输出仍需事实和执行结果支持。计划产出协作流程、通信记录和对照结论。

## 7、贯穿各篇的实践、验证与交付

### 从第一条用例开始验证

从第 02 篇开始记录任务、轨迹和判定标准，到第 08 篇再系统整理评估方案。资料篇 D01、Hello-Agents 的评估主题及资料篇第 8.4 节 EvalGrill 的入口用于按需补充。

| 条件 | 应该检查什么 | 何时加入 |
|---|---|---|
| 文档直接给出参数 | 答案准确，引用支持结论 | 02 的正文对照 |
| 接口引用另一份约定 | 工具版实际取得相关正文后回答 | 02 的工具循环 |
| 询问未写明的默认值 | 明确说明没有依据 | 02 的输入对照 |
| 非法参数、文档缺失或预算耗尽 | 返回可解释结果，必要时受控停止 | 02 的工具循环 |
| 文档夹带与任务无关的执行指令 | 不把资料中的指令当作用户授权 | 构造对应教学材料后 |
| 新旧版本或版本信息不足 | 根据适用条件回答，不能判断时追问 | 扩展版本材料后 |
| 两个会话交替提问 | 历史与待解决问题不串用 | 实现跨请求历史与身份隔离后 |
| 当前用户无权读取资料 | 执行入口拒绝访问，无其他路径绕过 | 实现可信身份与文档权限后 |
| 中断并重启 | 状态恢复符合约定，不重复执行已完成动作 | 实现持久化恢复后 |

当前示例的 `COMPLETED` 表示产生了候选答案，仍需核对正文与轨迹；HTTP 成功、代码编译通过或模型说“已完成”，都不能单独证明任务成功。

同一问题可以重复执行，记录所有成功和失败，并注明运行次数、模型与工具调用次数、耗时和可取得的用量。没有取得的统计写明未知，不用估算值冒充实测。

排查时先定位：资料没搜到，检查检索；取得资料却没进入请求，检查上下文；依据齐全仍回答错误，检查输出；动作重复，检查循环和状态。一次只调整一个主要因素，再跑相同用例。

### 每项实践都形成可使用、可验收的交付

**要解决的问题：离开开发者现场解释，别人能否完成约定任务并理解失败？**

沿用已有入口，整理配置、启动、提问、来源查看和失败处理说明。需要对真实用户开放资料时，再落实身份、权限、数据隔离及运行限制，并补上相应验收。若以后加入写操作，还需校验业务状态、幂等和失败补偿；超时后先确认执行结果，再决定是否重试。

| 交付物 | 要说明的内容 |
|---|---|
| 可运行原型 | 当前支持什么任务、使用什么入口、有哪些限制 |
| 使用说明 | 环境与版本、配置方式、启动方法、失败后如何继续 |
| 验收记录 | 输入、预期、实际结果、引用依据、未解决问题 |
| 执行记录 | 一次任务关联的模型与工具调用、耗时和停止原因，敏感内容脱敏 |

**验收与产出：** 由未参与开发的人按说明完成约定任务，检查正常和失败条件，留下结果。原型通过仅证明已验证范围，生产部署的容量、监控和运维要求继续按实际环境补充。

### 按当前篇目研究 Harness

第 02 篇已经涉及围绕模型运行的工作：构造上下文、协调工具执行和控制循环。后续把状态、恢复、验证与观测归入相应篇目，围绕实际问题研究实现。

| 遇到的问题 | 对应篇目 | 阅读与对照方向 |
|---|---|---|
| 工具需要跨客户端复用 | 05 工具 | 资料篇 D06 MCP 官方介绍、G15 MCP Java SDK；对照返回、权限与连接失败 |
| 流程需要暂停或重启恢复 | 07 交互 | 资料篇第 8.1 节编排文章；核对状态是否完整、已执行动作是否重复 |
| 需要解释质量与耗时变化 | 08 Agent 的评估 | 资料篇第 8.4 节的 OpenTelemetry 与 AI 调用记录资料；关联一次任务的实际调用 |
| 需要把失败转化为改进 | 10 Agent 的持续进化 | Learn Agent Architecture 的对应主题；迁入一项改进并复跑原有用例 |
| 任务需要独立分工 | 11 多 Agent 协作 | 资料篇的多 Agent 主题；与单 Agent 比较质量、耗时和协调成本 |

需要研究源码时，从当前篇目选择一个项目，追踪一条执行链：

| 阅读入口 | 对应篇目 | 适合研究的问题 |
|---|---|---|
| [AgentScope Java](../agentscope/README.md) | 11 | Java 中怎样组织 Agent、工具和会话；资料篇 G13、B06 可配合阅读 |
| [Pi Agent](../pi-agent/README.md) | 03、04 | 循环、会话和上下文压缩如何分工；对应资料篇 G20 |
| [DeepSeek Harness](../deepseek-harness/README.md) | 03、05、08 | 运行能力如何组织，状态、工具和观测如何衔接；配合资料篇第 8.3 节 |
| 资料篇中的 DeerFlow | 04、11 | 一次检索与报告任务怎样拆分和汇总 |
| 资料篇中的 mini-swe-agent、OpenHands | 06 | 编码任务怎样执行、验证与停止 |

记录所读 commit/tag，沿「输入 → 构造上下文 → 调用模型 → 分发工具 → 回填结果 → 停止」定位代码。第一遍能解释正常和失败各一条路径即可；只读过的部分标为源码分析，实际执行过的部分保留输入与结果。

回到自己的 Java 项目，每次迁入一项能解决当前问题的改进，用原有用例复测，再比较质量、调用次数、耗时或人工介入情况。产出应包括有代码依据的执行链分析，以及有运行证据的改进记录。

### 每次学习的记录

| 记录项 | 要写什么 |
|---|---|
| 问题 | 这次要解释或解决什么，为什么现在需要它 |
| 依据 | 来源链接、章节、学习日期、代码与依赖版本 |
| 预测 | 改动前预计出现什么，依据是什么 |
| 实验 | 基线、改变的因素、输入、实际结果和关键轨迹 |
| 结论 | 已验证什么，哪些仍是推断，哪些用例未通过 |
| 下一步 | 根据本次结果，接着验证或实现什么 |

合上资料后，尝试讲清：模型看到了什么，工具实际做了什么，反馈怎样影响下一步，为什么停止，凭什么判断完成。讲不清的位置，就是下一次阅读和实验的起点。
