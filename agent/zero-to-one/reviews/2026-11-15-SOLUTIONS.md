这里的数字全部来自本仓库真实报告 `weather-agent/target/weather-runs/run-5948179923749700326/report.json`（`promptMode=rules`、`contextMode=full`、`status=COMPLETED`），不是估算：

````markdown
**输入预算要按完整请求算。**下面是一次真实运行的记录，同一个天气任务在三轮工具往返中的输入增长：

| 轮次 | 消息 JSON 长度（UTF-16 单元） | 服务返回的输入 Token |
|---|---|---|
| 第 1 轮 | 584 | 779 |
| 第 2 轮 | 1649 | 1070 |
| 第 3 轮 | 1995 | 1153 |

```text

````

1. **给数字**。S1 之所以从第一轮悬空到现在，就是因为只有名词没有实例。上表两列并列，读者一眼能看到"584 → 779"和"1649 → 1070"不是同一比例。

## S2（P1）实验 3-1 的温度步骤被默认 top-p=0.8 叠加

### 已验证的事实

`SamplingLab.java` 的 `top-p` 默认值是 `"0.8"`，所以读者跑 `--temperature=0.5` 时会看到两行：

```
所选温度（未筛选）  A=0.8668  B=0.1173  C=0.0159
所选温度 + top-p    A=1.0000  B=0.0000  C=0.0000   保留候选=1
```

而 03:241 折叠答案给的是**未筛选**的 86.68%。读者预测"A 会更集中"，看到 100% 会归因给温度，两处数字对不上。

**`--top-p=1` 已经实测可用**，加上之后两行完全一致、保留候选=3，温度效应不再被掩盖：

```
输入 logits=[2.0, 1.0, 0.0]；T=0.5；top-p=1.0
T=1 基线（未筛选）  A=0.6652  B=0.2447  C=0.0900
所选温度（未筛选）  A=0.8668  B=0.1173  C=0.0159
所选温度 + top-p    A=0.8668  B=0.1173  C=0.0159
A 的概率变化=+20.16 个百分点；保留候选=3；贪心索引=0
```

### 方案：改正文一句话 + 改命令块三行

**第一步，正文 03:232 原句：**

> **第一步，先预测再揭晓。**固定分数，把温度从 `1` 分别改为 `0.5`、`2`。记录 A 的概率会怎样变化、最高分位置会不会变化。配套程序默认只显示输入和问题；写下 `--predict` 并加 `--reveal` 才显示分布，让读者先判断，再用计算修正解释。

**替换为：**

```markdown
> **第一步，先预测再揭晓。**固定分数、显式把阈值设为 `--top-p=1`，再把温度从 `1` 分别改为 `0.5`、`2`。**不加 `--top-p=1` 会看不准**：程序默认 `top-p=0.8`，会顺手筛掉尾部候选，那时"所选温度 + top-p"那一行是两个参数叠加的结果，`A` 可能直接变成 `100%`，很容易被误读成"温度让 A 更集中"。记录 A 的概率会怎样变化、最高分位置会不会变化。配套程序默认只显示输入和问题；写下 `--predict` 并加 `--reveal` 才显示分布，让读者先判断，再用计算修正解释。
```

**第二步，`prompt-labs/README.md:37-41` 三条命令改成：**

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --temperature=0.5 --top-p=1 --predict=填写你的预测 --reveal
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --temperature=2 --top-p=1 --predict=填写你的预测 --reveal
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --top-p=0.95 --temperature=1 --predict=填写你的预测 --reveal
```

**第三步，`README.md:43` 的解释句替换为：**

```markdown
一次只改变主要因素。温度实验固定 `--top-p=1`，让"所选温度（未筛选）"和"所选温度 + top-p"两行数值一致，这样看到的差异只来自温度；top-p 实验固定 `--temperature=1`，比较筛选后分布。再用 `--logits=0,2,1` 与 `--logits=0,0,0`，检查原解释在最高分换位、并列时是否成立。
```

**第四步（可选但推荐），03:241 的折叠答案加一句定位：**

在「`T=1` 时 A/B/C 约为 `66.52% / 24.47% / 9.00%`……」这段之前加：

```markdown
> 下表给的是**筛选前**的分布（`--top-p=1`）。若用默认 `top-p=0.8`，温度 0.5 时 A 会被筛到 `100%`，那是筛选造成的，不是温度造成的。
```

### 为什么必须显式写 `--top-p=1` 而不是只改说明文字

只改说明文字（"请看未筛选那一行"）是上一轮已经试过的做法，本轮实测证明**不够**：读者手上两条命令长得一样，输出里那行 `100%` 仍然最刺眼，说明文字在下面，先看到的是数字。`--top-p=1` 是把"两个变量"降成"一个变量"，属于从根上消除歧义，不是补注释。

### 验收

- 跑第二条命令，输出中"所选温度（未筛选）"与"所选温度 + top-p"两行**数值相同**、`保留候选=3`。
- 跑 `--temperature=2 --top-p=1`，A 约 `50.65%`，与 03:241 一致。
- `--self-check` 仍是 `PASS: 10 项`（本次改动不碰计算实现）。

## S3（P1）2.5 节四种多步方法，项目一种都没落地

### 先说一个关键事实：不需要新写代码

`DeepSeekPromptLab` 已经有完整的重复对照能力，只是正文没把它接进 2.5 的叙事：

- `comparePrompts`（`DeepSeekPromptLab.java:214-227`）是 `for repeat in 1..repeats { for promptMode in PROMPT_MODES { run(...) } }` —— 每一轮都是**独立的新任务**，不是同一对话的继续。
- `comparisonMarkdown`（`:494-548`）已经产出「重复 / 方案 / 累计增加内容 / 模型请求·工具执行 / 状态·停止原因 / 通过 / 错误项」表。
- `appendFieldComparison` 产出「字段并排对照」，按重复分组、五字段并列三方案。
- 还有一节叫「预测与原始候选」，每轮每方案给预测、候选，以及"与本次 basic 相比：文本相等=…；JSON 结构相等=…"。

也就是说，`--repeats=2` 打印出来的就是一份**两次独立采样对照表**。这正是"自我一致性"要解决的现场。

### 方案：在 03:262 之后插入一段（放在表格与论文链接之间）

```markdown
**重复观察能看见什么。**同一段提示词、同一条证据，跑两次未必给同一个候选。用 `--mode=compare --case=not-found --repeats=2 --predict=…`，`comparison.md` 的「预测与原始候选」一节会把每轮的 basic / rules / examples 并排列出，并标出"与本次 basic 相比"的文本相等与 JSON 结构相等。两轮里如果 basic 的候选不同，"自我一致性"要解决的问题就摆在你面前了：同一套输入下，模型的选择并不稳定。多数投票能压低随机波动，但**共同错误会被一起投出来**，所以它不能替代证据核对。本项目只做了重复观察，没有投票与汇总机制——这一步能演示动机，不能复现论文效果。
```

同时在 03:259 那一行（自我一致性）的末列微调为：

```markdown
| 自我一致性 | 为同一问题生成多条推导，汇总最终答案 | 需要定义答案等价与汇总规则；多数结果也可能一起错 | `--repeats` 保留重复观察与逐轮对照，没有投票或汇总机制 |
```

### 为什么不选"把 4 行表降级成选型说明"

报告里给了 (a)(b) 两个选项。这里选 (a)，理由：§2 前四节的节奏是"每个机制都能动手看"（2.1 有采样程序、2.2 有回放、2.3 有图、2.4 有实验），2.5 如果变成纯选型表，节奏断裂会保留下来。而 (a) 只花一段话，就把 2.5 接回这个节奏，成本极低。ToT / 反思与修订仍然诚实标"没有实现"——这一段只解决"自我一致性有现场"，不假装四种方法都落地。

### 验收

- `--repeats=2` 的 `comparison.md` 里能数出两轮记录，且「预测与原始候选」小节存在。
- 03:266 那句"每次只加入一个步骤要求或一种组织方法，用同一组任务比较收益与退化"现在有了入口，读者不再被指向一个不存在的功能。
- 边界：需要 `DEEPSEEK_API_KEY`，本机未跑；方案给的是命令与已有输出结构，不是实测结果。
