## 2. P1：影响学习闭环的问题

### S1（P1）路线图与正文结构脱节，且承诺的"上下文计算"未兑现

**路线图原文**（03:22）：

> 本篇先用活动通知练习任务表达，再解释 Token、上下文计算和生成策略；随后进入 Java 天气工具与固定数据实验，学习怎样组织消息、约束执行、检查结果和比较提示词效果。

两处对不上：

1. **未兑现的承诺**：路线图说"解释 Token、**上下文计算**和生成策略"。§2 有 Token（2.1）、生成循环（2.2）、注意力（2.3）、采样（2.4），但**没有任何上下文预算的计算**。全文术语统计：「上下文窗口」0 次、「上下文长度」0 次、「KV Cache」0 次、「模型权重」0 次；唯一沾边的是 03:167 一句「输入预算要看完整请求……应按所用服务的上下文规则为输入和输出留出空间」——没有数字、没有示例、没有计算方法。这一条从第一轮（R4 同类）到现在始终悬空。
2. **未预告的新内容**：本轮新增的 1.5（结构化模板，95-143 行）、2.5（多步调用，247-266 行）、5.4（评分方法，537-568 行）都不在路线图里。而 03:583 恰恰把这三节当作全篇收束：

   > 回头看，1.5 把零散条件装进填空表，2.5 分清"改一句话"和"改调用方式"，5.4 给出"怎样算更好"的评分表……其实是在回答三个不同层次的问题：信息怎样组织（1.5）、要不要让模型多想几步（2.5）、结果怎样才算过关（5.4）。

   也就是说：**作者心里的主线是 1.5→2.5→5.4 三层，路线图描述的主线是 §1→§2→§4/§5 的流程**，两套主线并存，读者读完开头建立的预期与结尾的收束不是同一件事。

**为什么这是 P1**：路线图是读者建立心智模型的第一个锚点。开篇说是"先学表达任务、再理解机制、最后做实验"，结尾却说"其实讲的是三个层次"，读者会怀疑自己漏读了一章。

**建议**（不代改）：路线图改写成能覆盖 1.5/2.5/5.4 的说法，或把三节的新增内容降到"延伸"定位；"上下文计算"要么补一段带数字的输入预算示例（例如把 03:7-18 那条通知按 token 估一遍），要么从路线图删掉。

### S2（P1）实验 3-1 的温度步骤仍被默认 `top-p=0.8` 叠加（第二轮 N1 原样遗留）

**正文承诺**（03:232）：

> **第一步，先预测再揭晓。**固定分数，把温度从 `1` 分别改为 `0.5`、`2`。记录 A 的概率会怎样变化、最高分位置会不会变化。

**读者实际会看到的两行**（本机 JDK 21 实测 `--temperature=0.5 --predict=x --reveal`）：

```
所选温度（未筛选）  A=0.8668  B=0.1173  C=0.0159
所选温度 + top-p    A=1.0000  B=0.0000  C=0.0000   保留候选=1
```

**问题**：`SamplingLab.java:36` 的默认值是 `top-p = "0.8"`（README:49 亦确认"默认 0.8"），所以温度实验实际是"温度 + 0.8 筛选"两个变量一起动。读者按提示预测"A 会更集中"，看到 `100%` 会归因给温度；而 03:241 的折叠答案给的是**未筛选**的 86.68%，两处数字不对应，读者无法判断哪个才是"温度的效果"。

**为什么这轮必须修**：上一轮已提出（N1, P2），本轮正文未动；而 2.4 节的分步设计让暴露概率更高——三步实验的第一步就撞上这个问题。

**建议**：命令块补 `--top-p=1`（`SamplingLab` 支持，`topP(baseline, 1)` 保留完整分布，代码 141 行有对应断言），或在 03:232 明说"温度这一步先看'所选温度（未筛选）'那一行，第二行是叠加默认 top-p 后的结果"。README:38-40 的三条命令都要同步。

### S3（P1）2.5 节讲四种多步方法，本项目一种都没落地

**正文自述**（03:257-262 表格最后一列）：

| 做法 | 本项目中的对应范围 |
|---|---|
| 自我一致性 | `--repeats` 只保留重复观察，没有投票或汇总机制 |
| ToT 思维树 | 没有实现 |
| 反思与修订 | 没有自动修订循环 |
| ReAct | 天气回放可观察工具请求与回填，不据此宣称实现了完整 ReAct 方法 |

四行里三行是"没有"，第四行是"不据此宣称"。这一列的诚实值得肯定（比硬凑对应关系好），但它带来一个教学后果：**这一节是全篇唯一"讲了但无法验证"的机制节**。

对比 §2 其他小节：2.1 有采样程序、2.2 有可视化回放、2.3 有 SVG 图、2.4 有实验 3-1。到 2.5，读者手上没有任何可运行的对照。而 03:266 给的实践建议——"每次只加入一个步骤要求或一种组织方法，用同一组任务比较收益与退化"——恰好是这个项目**没有提供入口**的事（5.2 已坦白"当前项目没有提供……完整重复评估入口"）。

**读者视角的问题**：前面四节刚建立了"每个机制都能动手看"的节奏，2.5 突然变成纯文献综述（三篇 arxiv 链接）+ 四行"未实现"表格。这个节奏断裂本身就是"深入浅出"的失败点：**读者会记住"有一种方法叫 ToT"，但不知道它和自己写的提示词有什么关系**。

**建议**：二选一——(a) 在 `--repeats` 上补一个最小可做的对照（同一提示词跑 2 次，把两次候选取并集/看差异，就能演示"多次采样结果不一致"这个自我一致性的**动机**）；(b) 承认这一节是"概念地图"性质，把 4 行表格改成"这些方法解决什么场景"的选型说明，不再挂"本项目对应范围"这一列——避免读者反复确认"我是不是漏配了什么"。

### S4（P1）全篇没有一份"合格清单"的成品对照

**测算**：正文 11 个代码块，§1 占了 5 个（03:7-18、54-62、76-85、109-122、130-135），**全部是"给模型的输入"**，没有一个展示"模型该输出什么"。

- 1.3 的唯一输出示例是**单字段**：「集合时间：13:50。」（03:58），且明说"下面只演示'集合时间'这一项"（03:52）。
- 1.2 用三类失败抽象描述（03:44-46）："通知写了，回答漏了 / 通知没写，回答补了 / 相关材料没进入输入"——每类都没有给出**失败回答的实际文本**。
- 1.4 给了完整的任务契约（7 行），但契约的**产物**——一份"活动时间、集合地点、报名方式、携带物品、待确认事项"五项齐全的清单——全篇没有出现过。
- 5.4 的评分表却要求读者按"相关性 / 准确性 / 完整性 / 格式遵循"（03:553-558）给答案打分，并举例"5 分示意：13:50 集合与 14:00 开始不混用，费用未知"。

**结果**：读者在第 26 行被要求"把一句模糊要求变成可执行任务"，到第 558 行被要求"给答案打 1~5 分"，中间**从未见过一份及格的成品长什么样**。"完整性 = 五项都有交代"这五项到底是什么形状，只能靠想象。

**为什么这是 P1 而不是 P2**：这是"深入浅出"里"出"的那一半。前三轮修的都是"解释得够不够清楚"，这一条是"有没有给出可对照的答案样本"。教材类内容缺成品，读者无法自评，5.4 的评分表就落不了地。

**建议**：在 1.4 或 1.5 末尾补一段 `text` 块，给同一通知的**两份输出对照**——一份及格（五项齐全、费用标"未提供"）、一份典型失败（把 13:50 写成开始时间、费用补成免费）。这两份输出后面还能在 5.4 复用（正好对应评分表的"5 分示意 / 1~2 分示意"两列），一次投入两处收益。

## 3. P2：建议发布前修

### S5（P2）1.4 的 7 项任务契约与 1.5 的 5 项分区表是两套结构，未说明关系

相邻两节各给了一套"提示词该有哪些部分"：

- **1.4**（03:76-85）任务契约 7 项：目标 / 材料 / 约束 / 完成条件 / 核查方法 / 交付 / 停止条件
- **1.5**（03:99-105）分区表 5 项：任务与受众 / 材料与背景 / 约束 / 输出 / 检查与停止

两套既不对齐也不交叉引用。1.5 开头只说"前面已经明确用途、材料、约束、输出和检查标准。把这些内容分区保存，就形成了可复用的提示词模板"（03:97）——读者会问：**刚才那 7 项和现在这 5 项，是同一件事的两种写法，还是两件不同的事？** 如果是前者，"完成条件/核查方法/交付"怎么合并成了"检查与停止"；如果是后者，何时用哪套。

另外 1.5 的 `# 角色/# 任务/# 格式/# 材料` 示例（03:109-122）只有 4 个分区，与上面 5 行表格也对不上："检查与停止"没有对应分区。

**建议**：给一句映射说明（"1.4 的七项可以合并成 1.5 的五个分区：完成条件+核查方法→检查与停止，交付→输出"），或直接统一成一套。

## 4. P3：文案与覆盖细节

### S12（P3）否定式密度过高，§2/§4 最重

全文否定式限定 74 处（「不能」34、「不是」16、「不要」7、「不等于」5、「不代表」5、「并不」3、「不足以」3、「无法」1）/ 13496 汉字 ≈ **每 182 汉字一处**。分节：

| 节 | 汉字 | 否定 | 密度 |
|---|---|---|---|
| §1 | 2309 | 7 | 每 330 字一处 |
| **§2** | 2988 | 21 | **每 142 字一处** |
| §3 | 849 | 4 | 每 212 字一处 |
| **§4** | 2068 | 14 | **每 148 字一处** |
| §5 | 3528 | 21 | 每 168 字一处 |
| §6 | 664 | 3 | 每 221 字一处 |

单看每一句都是准确的（大多是必要的边界提醒，如"温度为 0 也不保证线上完全一致"），但密度到每 142 字一处时，阅读体验会变成"**刚理解一个概念，马上被告知它不保证什么**"。这正是"防御性写作"的典型症状——作者被前两轮 review 要求"不要夸大"，于是每加一句结论就配一句消解。

**建议**：保留关键边界（涉及事实正确性的），把"预防性免责"合并成每节末尾一段"本节边界"。§2 可以砍掉 8-10 处。

### S13（P3）「上下文」一词 16 次，但从未定义

正文出现「上下文」16 次（22、126、141、159、167、168、198、200、202、208、214、216、317、577、589 等），其中包括 03:198 的小节标题「再往里看：模型怎样结合上下文」和 03:200 的首句「先计算上下文中的表示」。但**全篇没有一句解释"上下文"指什么范围**——是当前这次请求的全部输入？还是包括历史消息？"上下文窗口"一次都没出现。

对照 1.5 的长材料组织段（03:141）说"让当前问题靠近相关材料，是为了便于使用上下文"——读者此时还不知道"上下文"的边界，这句只能囫囵吞下。

**建议**：在 2.1 末尾或 2.3 开头加一句定义（"本次请求送进模型、可供它计算的全部 Token 序列，就是这次生成看到的上下文"），后面 16 处引用就都站得住了。这条与 S1 的"上下文计算"缺口是同一件事的两个面。

### S14（P3）OpenAI 链接域名在正文与参考清单中不一致
