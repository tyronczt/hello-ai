使用方式：从“开场”往下，普通段落就是可直接朗读的台词；引用块中的“操作”和代码块用于录屏，不朗读。按提示操作后，接着读后面的结果说明，各节可以分开录制。

## 开场：同一条通知，为什么会得到不同回答

> 操作：展示正文开头的旧书交换通知，先框出通知，再框出提示词。保留“教学演示”的说明。

我们先看屏幕上这条周末活动通知。假设我要去参加，出门前得弄清楚几件事：几点到、去哪儿集合、要不要报名、带什么东西。

我把通知丢给 AI，只说“帮我总结一下”。它可能给我一段活动介绍，读起来挺顺，可我真正要做的准备还是没列出来。

所以我会把这句话改具体一点：请把通知整理成参加前的清单，时间、地点、报名、物品分别列出来，没写的就标“未提供”。

你看，材料还是同一条通知，变的是我让它拿这些信息做什么。这个用来说明任务的输入，就叫提示词，也就是 Prompt。它可以很短，也可以带上材料、背景和输出要求。

这里有两个地方特别容易漏。活动下午两点开始，但一点五十分就要集合；通知没写费用，也不能顺手写成免费。回答到底能不能用，要拿这两点回头检查。

我们先设计这份输入，再根据回答查问题、改要求、做比较，这整个过程就是提示词工程。

今天就从这条通知开始，再看模型怎样处理这些文字。后面接上 Java 工具，亲手跑几个实验，看看一次回答该怎么检查。

## 1.1 从结果倒推需要交代什么

> 操作：并排展示简略要求“帮我总结通知”和正文开头的完整要求。若实际调用模型，使用相同通知和独立会话，保存两份原始回答；不要提前制作一份“优化后必然更好”的假输出。

先别急着换措辞，我想先确定一件事：拿到这份回答以后，我准备干什么。

我要去参加活动，就得安排时间、提前报名、准备物品。这样一想，需要保留哪些信息就很明确了。

所以我不会只补一句“再详细点”，而是直接告诉它：集合时间和开始时间分开写，报名方式和截止要求都要保留，通知没说的事项也要标出来。

这样写还有个好处，检查的时候我有东西可对照。报名漏了没有？两个时间混了没有？费用是不是自己补出来的？都能回到原通知里找到依据。

> 操作：展示图 1，依次指向目标、材料、约束、输出、核对。若两份实际回答都合格，口播补充：“这次两版都满足要求，暂时没有观察到差异。”

图里这几个位置可以当作写完后的检查顺序：我要什么，用哪份材料，有哪些限制，最后交什么，再拿什么核对。对这个任务，把这些说清楚就够了，不必再加一大段“你是某某资深专家”。

## 1.2 一次只针对看得见的问题修改

> 操作：在原通知中高亮“周五晚前在群里接龙报名”。接着展示三类问题的标题，不虚构模型实测结果。

假设清单还是不合用，我会先看它是哪一种错，再决定改哪里。

比如，通知明明写了“周五晚前在群里接龙报名”，清单里却没了。这是漏信息，我就补一句“保留报名方式和截止要求”，再跑一次看它有没有留下来。

另一种情况，通知根本没写结束时间，回答却给了一个确定时间。那我要改的是缺失信息的处理，告诉它没写就标“未提供”，不能让它继续补全。

还有一种，活动安排分在几条群消息里，我只贴了一条。模型这次没收到的内容，光改一句提示词是找不回来的，得先把材料补齐。

所以，看到错误以后，先找出是漏了、补了，还是没收到材料。原提示词和这次的输入、回答都存下来，每次针对一个问题改，改完还要看看有没有把别的地方弄丢。

## 1.3 用示例展示期望的处理方式

> 操作：展示正文中的两个“集合时间”示例。先只显示通知片段，让观众预测；再展开参考输出。

有时我已经写了规则，它还是分不清两个时间。那就给它看一个具体例子。

先看第一条：活动两点开始，一点五十分集合。我要提取的是集合时间，所以应该留下的是一点五十分。

再看第二条，只说了两点开始，没有集合时间。这里我能知道活动什么时候开始，但还不知道几点集合，不能直接拿两点顶上去。

这两个例子放在一起，想说明的判断就很清楚了：有依据就提取，没有就保留未知。

只给任务、不给示例，通常叫零样本提示；放少量输入和输出的示例，叫少样本提示。名字先记个大概，更要紧的是例子有没有讲到容易出错的地方，而不是同一种成功答案放了很多遍。

至于放几个，要看模型和任务。有的推理模型适合先用简洁要求试，有需要再加示例，不能把某个数量当成通用配方。

还有个很容易忘的地方：规则改了，示例也得跟着检查。前面说未知要保留，后面的示例却补了一个时间，这两段内容就在互相打架。

## 1.4 给任务定义完成和停止条件

> 操作：展示任务契约，按目标、材料、约束、完成条件、检查方法、停止条件逐项高亮。

整理一条通知，通常一轮就够了。但如果我要汇总多条通知，或者让程序反复查询、修改，就不能只告诉它“去做”，还得说清楚做到哪一步可以交付。

还是这份活动清单，我的完成条件是：五项都有交代，通知里有的忠实提取，没有的标明缺失。

比如费用没写，我仍然可以交一份清单，只要把费用放进待确认事项里。可如果连通知都没给，或者关键时间、地点互相冲突，那就要先补材料、做澄清。

> 操作：展示图 2，分别沿“满足条件后交付”和“缺材料或关键冲突后请求补充”的分支移动光标。

沿着这张图看，能分清两条路：材料够、检查也符合要求，就交付；缺材料或有关键冲突，就先说明情况，停下来等补充。

这套约定就是任务契约。分五项写，规定的是样子；五项有依据或标明缺失，才是完成条件；逐项对照通知，则是检查办法。三件事对应起来，程序才知道什么时候该结束。

## 1.5 把要求组织成可复用的模板

> 操作：展示分区版和最小版提示词。两版都使用同一条活动通知，不改材料。

前面这些要求，我们不用每次都重新写一遍。把相对固定的部分分开放好，就成了一份模板。

比如这一块交代给谁整理，这一块写怎样处理通知，再往下写输出要求。通知单独放在材料区，下次换活动，就换这里的内容。

这样做主要是为了方便检查和修改。要改输出形式，能找到对应位置；换一条通知，也容易发现有没有残留上一次的安排。

旁边这版更短，几行就把目标、依据、未知值规则和输出要求写完了。先用哪一版都可以，但好不好用，得拿同一组通知比较，不能只看谁的标题多、谁写得长。

再往应用里走一步：如果这份结果要交给 Java 解析，我就得看模型有没有结构化输出接口。Schema 能约束支持的字段和类型，可字段值是不是来自这条通知，仍然要另查。

不同厂商的配置也不一样，不能把一家的严格模式参数原样搬过去。我们的配套项目目前用的是提示词加 Java 校验，还没有启用这种原生 Schema 约束。

## 2.1 从文字到 Token

> 操作：展示正文的编码流程。无需展示一份虚构的真实模型切分结果；沿文字、编号、向量三个位置解释。

要求写清楚了，接下来看看这些文字进模型之前，先经过哪一步。

我们发过去的是文字，分词器会把它编码成一串编号。这里的编码单位叫 Token，对应的词表编号叫 Token ID。

“分词”这个名字容易让人以为，它就是按一个字、一个词往下拆。实际不一定：常见片段可能合在一起，少见的词可能拆成几段，标点和空格也可能参与切分。这样，有限的词表就能表示大量文本。

再往下看，编号还不能直接说明含义。模型要根据编号查到向量表示，再结合位置和上下文做计算。两个编号挨得近，不代表意思也挨得近。

这个过程跟写提示词直接相关的一点，就是别把字数当成 Token 数。我们要求“不超过两百字”，和接口限制输出多少 Token，是两回事。

还要算完整输入。通知、规则、历史消息，后面会看到的工具定义和结果，都可能占空间。重要材料没进这次输入，模型就少了一部分依据。

所以，补上“费用未知就标未提供”，确实改变了这次输入，也可能改变后面的回答。但通知没写的真实费用，并没有因此出现；模型也没有因为这句话就重新训练一遍。

## 2.2 模型逐步生成，而非一次查出整篇答案

> 操作：展示图 3。公式只用于说明依赖关系，无需逐个朗读符号。

输入准备好了，生成时模型就会反复做同一个动作：根据当前输入和已经生成的内容，算下一步有哪些候选，选出一个 Token，接上去，再算下一步。

所以这里的“逐步”，说的是一个 Token 接一个 Token，不能直接理解成一个汉字接一个汉字。

还是费用这个例子。前面写了“通知没写的信息标未提供”，那么生成到“费用应标为”这里，后面接什么，就会受到这条要求和前文的影响。

但这里先别把“更符合要求”和“已经核实事实”混在一起。即便它最后写了“未提供”，我们也还是要回原通知检查。

普通请求里，变的是这次输入的条件；通过训练更新模型参数，那是微调要做的事。我们现在写的这些要求，作用在前一种过程里。

## 2.3 模型怎样结合上下文

> 操作：展示图 4，依次指向输入表示、注意力、多层变换、下一 Token。强调上下文位置与候选 Token 两种不同对象。

刚才图里有一个“模型计算”的框，现在把这个框展开一点。

模型先拿到每个位置的向量表示，再通过注意力机制，把当前能用的上下文信息汇集起来。这里会用到查询、键和值，也就是图上的 Q、K、V。对因果生成，当前位置不能去用还没出现的未来内容。

这一段最容易看混：注意力的权重，是分给上下文里各个位置的；我们还没走到“下一 Token 选谁”那一步。

再经过多层计算，最后才得到词表中各个候选的分数，也就是 logits。把分数转成概率以后，才交给生成策略选择。

回到通知，规则、材料和示例都会影响这条计算过程。但某个注意力权重大，就不能直接解释成“这句话一定让回答更准确”。它还不足以说明这次回答为什么对、为什么错。

## 2.4 实验 3-1：温度与 top-p 改变什么

现在已经有候选分数了，下一步怎么选，还会受到温度和 top-p 的影响。我们用一个小程序把分数固定住，就能单独看这两个参数。

> 操作：在 `zero-to-one/prompt-labs` 目录打开终端，确认使用 JDK 21。先显示问题，不揭晓。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java
```

先别揭晓，屏幕上只看输入：A、B、C 三个候选，分数是二、一、零。这是人工设定，不是从真实模型里抓出来的分数。

程序给 A 起的名字是“编造恢复时间”。把它放回通知里，可以类比成补出一个没依据的费用：我们故意把错误候选放在最高分的位置，看看改参数能不能解决事实问题。

我先猜一下，温度降低以后，A 还会排第一，只是概率会更集中。

> 操作：两次都固定 top-p 为 1，先比较筛选前分布，避免把温度与筛选效果混在一起。预测文字可换成录制者自己的判断。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --temperature=1 --top-p=1 --predict=记录基线 --reveal
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --temperature=0.5 --top-p=1 --predict=最高分位置不变 --reveal
```

看“筛选前分布”这两行。温度是一的时候，A 大约占百分之六十六点五二；降到零点五以后，升到百分之八十六点六八。排在第一位的还是 A。

这组结果告诉我们，降低温度可以更集中地选择一个候选。可这个候选本来就是错的，更集中也不会把它变对。

接着保持温度不变，把 top-p 从零点八改成零点九五。这里先猜的是，会留下几个候选。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --temperature=1 --top-p=0.8 --predict=先判断保留几个候选 --reveal
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --temperature=1 --top-p=0.95 --predict=先判断是否会保留三项 --reveal
```

零点八这组，累计到 A、B 就达到阈值了，所以留下两项，再重新归一化。零点九五这组则把三项都留下了。

它改变的是候选范围。这次程序只算分布，没有真的抽样，更没有评出哪份回答质量高。

> 操作：如需补充边界，运行全零分数，并显示固定自检。全零时温度变化不会凭空制造偏好。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --logits=0,0,0 --temperature=0.5 --predict=三项应相等 --reveal
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' SamplingLab.java --self-check
```

全零这组，三个候选的分数相同，改温度也不会凭空造出一个偏好。最后的自检则是在确认这些计算和边界处理有没有按预期工作。

这两个结果都先停在它能说明的范围里：我们看清了选择机会怎么变，至于内容有没有依据，还得回材料检查。

## 2.5 区分步骤提示与多次调用

> 操作：展示正文的组织方式表，按四行展开，不展示不存在的项目实现。

刚才我们改的是选择参数。另一个常见想法是，让模型先多想几步，再回答。

这里要分清：在一次请求里要求它写出步骤，和为同一个任务生成多条候选、再组织后续交互，是不同的做法。

思维链提示，是引导模型先生成中间推导，再给结论。写出来方便我们看，但步骤也可能错，不能把它当成内部计算的完整记录。

如果模型已经具备推理能力，就先看它自己的指南。有的指南建议把目标、限制和必要材料直接说清楚，通常不必再加“一步一步思考”。

再看应用还能怎样组织过程。

自我一致性会生成多条推导，再汇总答案。这样能比较不同路径，但多数答案一致，也可能一起错。

思维树会把几个中间方案展开，评价以后再往下走，必要时回退。这里要有能判断方案好坏的办法，还要控制搜索成本。

反思与修订，就是先写一版，再挑问题、再改。可如果始终没有独立依据，模型也可能漏掉自己的错误。

ReAct 则把推理、行动和环境反馈交替接起来。行动取得外部信息以后，再继续判断下一步。

我们的天气项目后面能看到工具请求和回填，但不能仅凭这个，就说这些研究方法都实现了。重复次数参数也只是在保留观察，没有替我们做答案投票。

## 3.1 用消息角色保留来源和用途

> 操作：打开 [天气历史回放](prompt-demos/three-model-calls/index.html)，展开第一轮消息。它是历史记录，不重新发起查询。

多步任务要接得起来，应用就得把每一步的信息交给模型。我们先不发新请求，打开这次天气任务的历史回放，看它当时到底收到了什么。

第一轮里，用户消息说的是这次要问什么，系统消息放的是应用的规则。工具定义另外列出来，告诉模型可以请求哪些动作。

模型提出工具请求以后，Java 去执行；返回的工具结果再放进下一轮，供模型继续使用。

所以你看，下一轮多出来的内容，是应用保留、回填进去的。我们要检查模型依据了什么，就得看这些实际消息。

这里还要分清，真正的消息角色由程序设置。普通文本里写一个 system 标签，并不会自动取得系统消息的身份。

同样，外部资料里就算夹了一句“忽略此前规则”，也不能因此多出一份授权。来源要标清，工具和参数的边界仍然要由程序检查。

## 3.2 长期规则与运行消息分工

> 操作：展示正文中的 AGENTS.md 示意，再打开 WeatherPrompts.java 与 WeatherContext.java。不要将示意文件说成天气模块已经配置的文件。

说到规则，写项目时还有另一种常见文件，叫 AGENTS.md。构建命令、代码约定这些反复要交代的事，可以放在里面。

但这里很容易混成一件事：它指导的是帮助我们开发项目的编码 Agent。

天气应用运行时发给模型什么，是另一条路径。看这两处 Java 代码，规则从常量里取出来，再跟用户问题组装成消息；它并没有自动读取项目里的 AGENTS.md。

所以检查的时候，不能只说“文件里已经写了这条规则”。还得顺着代码往下看，这次请求到底有没有把它带上。

## 4.1 天气任务：先确认目标，再引用预报

> 操作：展示天气工具边界图和 WeatherTools.java。这里先读代码，不声称已经发起实时查询。

通知可以直接贴给模型，可北京明天的天气，得去外部服务查。接下来这个案例，就比刚才多了一步：先取数据，再根据数据回答。

要判断明天要不要带伞，第一步先定地点，再根据当地时间确定“明天”是哪一天，最后找到那一天的预报。

看工具里的这个字段。当前适配的高德预报没有降水概率，项目就保留 null，表示未知。不能因为是空值就改成零，也不能看见“晴”就反推出一个概率。

时间也不能混用。查询时的当地时间用来理解“明天”，预报日期用来选那一天的数据，发布时间和获取时间又各有含义。日间、夜间温度，也不能直接改叫最高、最低温度。

所以天气回答里的事实，并不是写得像预报就可以了。每个字段都得找到对应的工具依据。

## 4.2 三种提示词怎样比较

> 操作：打开 WeatherPrompts.java，展示组合 switch 与三种常量。同步展示图 7。

这段代码里，一次任务会选一版提示词。我们先把三版之间的关系看清楚。

basic 用的是共有内容；rules 在这上面加流程规则；examples 再往里加示例。屏幕上这个拼接关系，就是这么一层层加的。

因此，basic 里也有事实边界。不能拿它当成一份完全没有规则的提示词。

还有一点，rules 一次加了好几项要求。即便后面观察到差异，也得先记在整套方案上，不能立刻说是某一句话起了作用。

示例里的工具结果同样只是在演示。真正回答这次天气，还是要等本次查询拿到数据。

## 4.3 提示词之外，Java 决定什么

> 操作：在 WeatherContext.java 展示 SystemMessage 与 UserMessage 的组装，在 WeatherTools.java 定位地点 ID 检查。

模型拿到这些规则以后，可以提出工具请求。但要实际执行，还得先过 Java 这边的检查。

比如天气查询用的地点 ID，必须是本次检索登记过的。模型写出一个看起来合理的编号，也不能直接拿去用。

所以，这两边各有一份工作：提示词把任务和处理方式说清楚，Java 检查参数、访问范围和预算。

我们以后改提示词常量，也别忘了重新构建、启动。最后再看新报告，确认真正发出去的文本已经变了，才算跑到了新版本。

## 4.4 实验 3-2：字段齐全为什么还可能错

工具能运行，还不等于最后答对了。我会把检查分开看：先看结构能不能解析，再看动作有没有依据，最后核对答案里的事实。

比如，JSON 能解析，只说明结构这一步过了；有没有擅自选城市、有没有重复查，要看行为记录；地点、日期和概率是不是写对了，还得对照工具结果。

下面这个离线实验，就专门把字段和证据拿出来给我们练。

> 操作：展示结构、行为、结果三层图。随后回到 prompt-labs 目录，先显示问题。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' EvidenceCheckLab.java
```

现在看到的是一份固定的合成天气证据。日期是教学用的固定日期，不是录制当天的预报。

里面的概率是 null，也就是未知。我先故意把候选里的概率填成零；再做一组，把日期和时区同时改错。先猜一下，程序分别会指出什么问题。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' EvidenceCheckLab.java --probability=0 --predict=未知不能填零 --reveal
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' EvidenceCheckLab.java --date-offset=1 --timezone=UTC --predict=应有日期和时区两项差异 --reveal
```

第一组这行 PROBABILITY，说的是概率不一致。原来没拿到概率，候选却写了一个确定的零，这就变成了另一个意思。

再看第二组，DATE 和 TIMEZONE 一起出来了，因为我同时改错了日期和时区。它们的类型都可以合法，但和这次证据仍然对不上。

接着试一个更容易忽略的情况。我把证据和候选一起换到另一个地点，请求的目标地点保持原样。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' EvidenceCheckLab.java --evidence-location=310000 --location=310000 --predict=错误地点的证据也不适用 --reveal
```

这里先返回 EVIDENCE_MISMATCH。两边虽然相同，可这份证据本身就不属于当前请求，不能拿它继续给答案作证。

最后再看，字段都相同的时候，它还有什么看不见的。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' EvidenceCheckLab.java --case=prose-conflict --predict=字段检查读不到附带文字 --reveal
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' EvidenceCheckLab.java --case=forged-evidence --predict=相等不能证明来源真实 --reveal
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' EvidenceCheckLab.java --self-check
```

第一种是字段没问题，附带的文字却在编造。核验器没有收到那段自然语言，自然检查不到它。

第二种是证据和候选一起伪造，字段也能相等。但一个来源标签写在对象里，并不能证明数据真的经过了可信的采集。

所以看到空错误列表，我会先问它检查到了哪一层，不能直接说整份回答可靠。最后的自检也一样，说明这些预设案例被按预期处理了，不是模型准确率。

这个问题故意没给城市。我想检查的是，它会不会先追问地点，有没有自己选一个城市就开始查，也不能在没有依据时声称已经查到了天气。

现在先读这次的实际回答，再打开对应的报告。光看最后一句“请补充城市”还不够，也要看工具记录里有没有发生不该发生的搜索。

再换成这句没有出现在示例里的问法，就更值得看了。这里既缺地点，也没有明确周末哪一天。我们要看它有没有指出缺少的条件，还是直接替用户做了假设。

## 5.2 固定条件，才谈对照

> 操作：展示图 9，再并排展示两份实际报告的配置、输入和工具结果；没有可比较的实际报告时只讲方法，不制作假结果表。

刚才两次请求，哪怕答案不一样，也不能马上归到提示词上。因为我们查的是天气，数据本身会变。

假如一版上午跑，另一版下午跑，连预报都变了，就很难说清差别是怎么来的。

所以，要比较提示词，我会尽量把其他条件固定：模型、参数、问题、工具定义、数据快照、日期锚点、评价标准，都按同一套来，轨迹也留下。

当前天气入口还是实时探索，没有冻结天气数据的完整评估入口。那份历史回放，只能说明当时那一次的过程。

接下来我们换一份固定数据。先把实时变化排除掉，再看模型面对不同提示词，会怎样查询和回答。

## 5.3 实验 3-3：线上模型与固定故障工具



### 5.3.1 明确独立用例和契约

> 操作：打开 DeepSeekPromptLab.java，展示固定用例、BASE/RULES/EXAMPLES 和工具定义。

这个实验换成了一个有查询编号的故障报告工具。报告是程序里的教学数据，不是生产记录。

这里特意换成可以固定返回内容的工具，再让模型按一份明确的 JSON 要求来回答。这样，工具数据不会每次变，程序也容易逐字段检查。

它跟活动清单有一个共同点：材料里有的照实提取，缺的别补。但交付格式不同，这里固定是五个 JSON 字段。

模型服务在远程，执行工具的 Java 在本机。工具只读本地的教学夹具，不查询天气，所以这一项不需要高德 Key。

比较的时候，用例、模型配置、参数、工具和核验规则都不变，只换系统提示词。每项任务重新开始，也不会接着上一项的消息或查询记录往下跑。

默认用的是“报告没找到”这个用例，示例里没有直接放这个边界。我们先写下预测，再看实际记录，不能提前把 basic 判成失败，或认定 examples 一定更好。

### 5.3.2 按服务、普通回答、工具、对照四步运行

前面知道了要比较什么，现在按四步来跑：先确认服务，再看普通回答，然后做一次工具往返，最后才比较三版提示词。

> 操作：切换到 weather-agent 模块目录。终端需已配置模型凭据；IDEA 用户也可直接运行主类并填写 Program arguments。先编译并生成类路径，确认每条命令成功后再继续。

```powershell
mvn -q -DskipTests compile dependency:build-classpath '-Dmdep.outputFile=target/prompt-lab-classpath.txt'
if ($LASTEXITCODE -ne 0) { throw '编译或类路径生成失败。' }
$labClasspath = 'target/classes;' + (Get-Content -LiteralPath 'target/prompt-lab-classpath.txt' -Raw).Trim()
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' -cp $labClasspath example.weather.lab.DeepSeekPromptLab --help
```

先编译，再生成类路径。帮助里列出的几个模式，也在这里确认一下。

接下来运行连接检查。这一步只请求模型列表，还不生成回答。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' -cp $labClasspath example.weather.lab.DeepSeekPromptLab --mode=check
```

检查结果出来以后，先看列表里有没有当前配置的模型。返回了合法列表，还不等于这一步检查通过；模型没列出来，就先把配置或访问问题处理好，再往后走。

服务这一步通过以后，先不挂工具，做一次普通回答。这样能单独看清楚消息发了什么、候选回了什么。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' -cp $labClasspath example.weather.lab.DeepSeekPromptLab --mode=chat --predict=先观察消息与候选
```

> 操作：打开本次 report.json 的 runs[0].rounds[0].request.messages，定位 role 与 content；再读原始候选。这个阶段只检查正常结束的非空文本，解释是否正确仍需人工判断。

在这里找两条消息的 role 和 content，跟原始候选放在一起看。这一阶段通过，只说明拿到了正常结束的非空文本，解释本身对不对，还是要自己读。

普通请求看清楚了，再加上工具。这次选的是恢复时间缺失的报告。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' -cp $labClasspath example.weather.lab.DeepSeekPromptLab --mode=tools --case=unknown --prompt=rules --predict=先查询并保留未知
```

> 操作：按本次实际轨迹依次展示 request.tools、模型 tool_calls、toolEvents、下一轮 messages 和 answer。若程序拒绝调用或没有形成候选，展示实际停止原因，不按成功路径继续讲。

读这份记录，我会顺着几个位置往下找。先看模型请求了什么工具、什么编号，再看 Java 有没有真的执行，最后看结果怎么回到下一轮消息里。

合法请求也得先过整批校验，Java 才去读数据。回填时，原 assistant 消息要保留，工具结果还要带上对应的调用 ID，这样才能和前面的请求配起来。

然后才看最终候选。恢复时间有没有保留 null？其他字段有没有忠实提取？有没有猜中字段，却根本没查这次的工具？

还有个格式细节，这里的未知必须是 JSON 的 null。写成字符串“未提供”，虽然人能看懂，却不符合这次的固定要求。

这一轮的轨迹看完了，再让三版提示词面对同一个用例。

```powershell
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' -cp $labClasspath example.weather.lab.DeepSeekPromptLab --mode=compare --case=not-found --repeats=1 --predict=先记录三版可能的行为差异
```

> 操作：打开控制台打印目录中的 comparison.md，再回到 report.json。每项请求可能产生线上用量。

先打开这份可读对照，看看三版各自做了什么；需要追到某条原始消息时，再回 report.json。下面我们就按这个顺序解释结果。

### 5.3.3 先解释状态，再解释差异

> 操作：依次高亮比较表中的实际运行数、停止原因、工具次数、字段、原始候选和检查项。

这张表我会先看实际运行了几项。

比如第一项就遇到服务错误，程序停止了，后面两项根本没运行。那两项不能记成失败，更不能拿它们算一个失败率。

再看每项停在哪里。服务请求失败，是没有取得可用的模型输出；程序拒绝工具调用，是行为触到了检查边界；已经拿到候选但字段不合格，又是另一回事。

工具说报告不可用，模型如实说明缺口，反而可能符合这个任务。不能把它和“模型服务没请求成功”混在一起。

再往下看文本和字段。两份 JSON 字段顺序不一样，文本就可能不同，但结构和值仍然可以一样。即便字段都对了，工具依据也还要单独看，不能让猜中的答案代替一次真实查询。

如果三版都通过，就如实记下：这个样本上，没有观察到契约通过情况的差异。再看实际回答和工具次数，不为了证明某版更好，只挑对自己有利的记录。

最后留意预算，每项最多四轮模型调用、三次工具执行，没有无限重试。后面真要研究某一条规则，就把其他条件固定，只改这一条，再重新编译；从请求里确认文本变了以后，才开始比较。

## 5.4 怎样判断一版提示词值得保留

> 操作：回到活动通知，展示正文的四维评分表。可展示一份“人工核对用参考清单”，明确它不是模型实测输出。

刚才我们能解释一份报告了，但要决定某版提示词值不值得留下，还不能只靠这一题。

回到活动通知，我会准备几种情况：信息齐全的、缺费用的、只写开始时间的，还有关键安排互相冲突的。再留几条不放进示例，看看换个输入还能不能处理。

评分之前，先把标准写出来。比如这张表，相关性看它是不是在帮我准备参加活动；准确性看一点五十分集合和两点开始有没有混，费用有没有被补成免费。

完整性再看五项有没有交代，缺的有没有标明。最后才是格式，是否按五项列出，有没有超过要求的长度。

比较时，把同一条通知下两份答案的版本名遮住，再去判断。逐题看哪些地方修好了、哪些地方反而错了，比只看一个平均分更容易找到问题。

程序可以检查明确字段，也可以请另一个模型辅助评分，但范围得讲清楚。模型裁判可能偏爱排在前面的、较长的，或某类风格的答案，也需要拿人工判断过的样本校准。它给了高分，不等于事实就已经核实了。

## 6. 收尾：四个问题和一条边界

> 操作：展示正文最后的四项检查，再展示资料与指令的边界图。结尾停留在活动通知与工具报告两个画面的对照上。

回到最开始那条通知，下次我再写提示词，会先想清楚，拿这份回答到底要做什么，模型能依据的材料又有哪些。

接着把交付要求写具体，哪些内容必须有，缺了怎样说明，遇到什么情况要先停下来。这样拿到结果以后，我才有办法一项项检查。

接上工具以后，还要再看程序替我们管住了哪些边界。能解析、工具动作合理、最后的事实对得上，这几层要分别核对。资料里夹着一句命令，也不能因此取得执行权限。

如果这套要求会反复用，就把规则和示例留下来，后面改了业务要求，也记得一起更新，别让旧例子继续带偏判断。

从这份清单到后面的工具实验，我们一直在做同一件事：把任务说明白，把依据给到位，再拿实际结果回来检查。做到这里，才知道下一次该改的是哪一句话，还是哪一步程序。
