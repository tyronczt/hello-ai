# Javaer 转 Agent：上下文工程

[上一篇](03-prompt-engineering.md)让天气助手知道怎样处理问题：确认城市和日期，取得真实天气，区分事实与建议。但规则写清楚之后，仍然可能回答错。Java 已经查询了明天的预报，模型却只回答当前温度；用户要求比较两个城市，经过几轮调用后，答案只剩一个城市。

这时先不要继续堆叠提示词。应该检查：**模型做这一次决定时，究竟收到了什么？**

本篇继续使用 [weather-agent](weather-agent/README.md) 与真实 Open-Meteo，沿消息构造、工具回填、状态更新和压缩逐步观察。第 02 篇的文档助手保留原实现；原来的六组文档实验与历史验证记录见[文档案例历史版](archive/03-context-engineering-docs.md)。

## 1、从一段提示词走向每一轮输入

### 1.1 同一个问题，不同轮次需要不同信息

仍然从这个问题出发：

> 北京市明天的天气怎样？请说明降水概率，并给出带伞建议、目标日期和来源。

首轮只有任务、规则和工具定义。城市检索之后，模型才获得地点 ID、行政区和坐标；天气查询之后，模型才获得当前条件、预报日期、概率和单位。一次任务中的信息随着行动推进，下一轮输入必须反映已经发生的事情。

如果只在 Java 变量中保存天气，不把它放回模型输入，模型就没有看到这次查询结果。反过来，整份天气返回已经进入请求，也不保证模型一定选中正确日期。上下文工程负责准备信息，回答核验还需要检查模型是否正确使用了信息。

### 1.2 三种状态不能混为一谈

| 位置 | 天气示例中的内容 | 负责什么 |
|---|---|---|
| Java 应用状态 | 本次候选地点、已完成工具批次、调用计数 | 记录实际发生的动作与结果 |
| 本轮上下文 | 规则、用户问题、选出的工具历史、状态快照 | 提供当前决策所需的信息 |
| 模型服务内部计算状态 | 与输入有关的计算中间结果，例如 KV Cache | 可能复用一部分计算 |

应用记住了地点 ID，不等于模型下一轮知道这个 ID；模型服务可能使用缓存，也不等于应用拥有跨会话的用户记忆。三者解决不同的问题，诊断时要分别取证。

这也是提示词工程与上下文工程的衔接点：前一篇主要研究工作要求怎样表达，本篇进一步决定每轮要提供哪些事实和历史、放在哪里、何时更新，以及怎样移除不再需要的信息。

## 2、一次工具循环怎样改变上下文

### 2.1 消息角色与工具定义分别在哪里

当前 Java 实现使用以下结构：

| 组成 | 来源与用途 |
|---|---|
| system 消息 | 应用选定的固定任务规则 |
| user 消息 | 用户原始问题；另有带明确标记的应用状态和检查点 |
| assistant 消息 | 模型的回复或工具调用请求 |
| tool 消息 | Java 实际执行后产生的工具结果 |
| tools 定义 | 工具名称、描述与参数 Schema，由模型选项注册 |

tools 不是另一种消息角色。它说明可以请求哪些动作；tool 消息说明某个动作实际得到了什么。

本例把状态和检查点放在带标记的 user 消息中。这是当前实现选择的承载位置，不代表终端用户又发送了一条指令。报告与消息标记会区分来源，但这种标记本身也不是权限机制。

### 2.2 城市检索与天气查询存在数据依赖

一种可能的执行过程如下。它用于解释数据依赖，不是预设真实模型必须采用的固定轨迹。

| 调用前 | 模型已经能看到什么 | 可能提出的动作 |
|---|---|---|
| 第一次模型调用 | 原始问题、任务规则、两个工具定义 | 搜索北京市 |
| 城市结果回填后 | 以上信息，加候选地点与实际 ID | 选择匹配地区的 ID 查询天气 |
| 天气结果回填后 | 以上信息，加时间、单位、当前条件和逐日预报 | 回答、说明缺口，或继续取得必要信息 |

本例的 `getWeather` 只接受本次搜索取得的 ID，因此天气请求不能凭空先于地点解析执行。如果需要比较两个城市，城市搜索请求可以出现在同一模型响应中；这不自动意味着 Java 底层已经并行访问网络，实际执行方式还要看工具执行组件。

如果用户没有提供城市，合理的下一步可以是追问。任务得到候选回答与任务取得完整天气答案，是两个不同的结果。

### 2.3 结果必须与原调用配对

模型生成工具请求时带有调用 ID。Java 执行后，返回消息用对应 ID 关联结果。地点 ID 标识查询对象，工具调用 ID 标识一次动作，不能混用。

例如同一响应里请求查询两个地点，下一轮必须包含这两个调用及各自结果。只留下一个结果、先插入状态再补另一个结果，都会破坏批次关系。不能把这种协议错误当作「模型没有理解上下文」。

[WeatherAgent.java](weather-agent/src/main/java/example/weather/WeatherAgent.java) 在完整执行之后才更新消息：

```java
var history = manager.executeToolCalls(prompt, response).conversationHistory();
prompt = new Prompt(context.afterTools(history, round, toolCalls), options);
```

[WeatherContext.java](weather-agent/src/main/java/example/weather/WeatherContext.java) 的 `validatePairs()` 检查配对，再把最后一个完整批次登记到本次任务中。当前实现还会在执行前整批检查工具名称、参数与调用 ID，防止部分工具已执行后才发现同批其他请求不合法。

## 3、信息够用，比信息齐全更具体

### 3.1 一条天气事实需要保留哪些条件

只保存一个温度数值，无法回答它属于哪个城市、哪个日期、什么单位。只保存「可能下雨」，也无法区分这是服务预报、模型建议，还是一次失败调用后留下的旧回答。

天气工具因此保留以下信息：

- 查询地点及其地区信息，避免同名城市混用。
- 服务返回的时区、天气有效时间和逐日日期。
- 数值与对应单位，未知值保持 null。
- Open-Meteo 来源、实际查询地址和本次获取时间。
- 当前条件与逐日预报的原始字段，外加确定性的天气编码说明。

这些字段不是为了让结果更长，而是为了使一句天气结论能够回到具体依据。Open-Meteo 的 current 使用气象模型数据；daily 是预报。当前条件的有效时间与 `retrievedAt` 的获取时间也应分别解释。[官方字段说明](https://open-meteo.com/en/docs)

### 3.2 未知与失败不能被压成零

某天的降水概率为 null，说明这次返回没有提供该值，不能改成 0%。搜索没有命中、服务限流、天气数组格式错误，则分别说明不同的失败。

这些差异决定下一步：搜索失败可能需要补充地点；服务失败可能需要说明暂时不可用；已有温度但缺少概率时，可以回答已取得的信息，同时标出概率缺口。把它们统一压成「无天气」，会丢掉可以继续使用的依据；统一压成「晴」，则制造了不存在的事实。

本例工具返回 `status` 和错误码。错误结果同样进入模型上下文，失败调用也消耗工具预算。失败不是一次没有发生的动作。

### 3.3 相关性取舍应从问题出发

查询明天是否带伞，逐日日期和降水概率有直接作用；完整小时级数组未必必要。本例只请求当前条件与三天逐日预报，以控制返回范围，尚未实现根据用户问题动态选择气象字段。

这是示例的能力边界。用户询问未来一个月的天气时，不能靠提示词把三天数据变成一个月，也不能将范围外日期映射到今天。下一步应该说明当前工具的范围，或在另行扩展服务能力后重新查询。

## 4、为什么稳定前缀与缓存有关

### 4.1 JSON、Token 和模型计算不是同一层

Java 构造消息对象，客户端把它转换为 HTTP 请求，模型服务再按自身协议与聊天模板处理输入。因此，Java 对象字段的排列、JSON 字符数和模型输入 Token 数不能互相替代。

本例报告中的 `messageJsonUtf16Units` 统计的是消息视图 JSON 的 UTF-16 单元数，包括字段名、标点和转义。它用于比较本程序构造的输入体积，不是 Token 计数，也没有包含 tools Schema。

最终 HTTP 请求还可能包含客户端补充的选项。报告明确标记为 Spring AI Prompt 视图，不能把它描述为对真实模型服务的完整抓包。

### 4.2 KV Cache 复用的是什么

在因果注意力模型中，当前位置利用查询向量 Q，与可见位置的键向量 K 计算相关性，再汇总值向量 V。追加后续 Token 时，之前位置不依赖未来 Token，因此已有 K、V 可以在相应条件下复用。

这里的 K、V 是模型计算中的向量，不是天气数据库中的键和值。KV Cache 也不是把上一次答案原样拿回来。一次生成内部的计算复用，与服务商跨请求提供的前缀缓存，是相关但不同的层次。

对常见的精确前缀复用，越靠前的变化越可能提前打断共同前缀。固定规则保持稳定、运行信息在后面进入，通常更有利于保留连续相同的输入部分。具体是否命中、节省多少，还取决于模型、模板和服务端实现。[机制讨论参考](https://bojieli.github.io/ai-agent-book/astro/book/chapter2/)

### 4.3 稳定性不能凌驾于信息正确性

天气项目在一项任务中固定提示词版本与工具定义，后续观察追加到历史。状态快照则每轮替换，避免同时出现多份「剩余预算」；压缩也会改写旧历史。

这两种操作可能损失部分前缀复用，却可能让输入更清楚或更短。判断时应比较实际信息保留、用量和耗时，不能只凭「前缀稳定」选方案。

当前天气项目没有采集服务端缓存命中统计，也没有完成真实模型成本对照。系统规则没有变化，只能说明这一段输入保持稳定，不能据此报告缓存命中率。

## 5、运行状态怎样帮助下一步决策

### 5.1 历史与状态承担不同职责

完整历史能说明先后发生了什么，却可能需要模型反复从头统计进度。状态快照把应用已知的事实集中表达，例如已经调用模型几次、还剩多少工具预算、已经完成多少批次。

在 state 模式中，`afterTools()` 用 Java 实际计数生成一个新快照，放在完整工具批次之后。重建下一轮时替换上一份快照，避免旧的剩余次数继续混入当前信息。

这没有新增天气事实，也没有训练模型。它只是把程序已经知道的进度以明确形式提供给模型。

### 5.2 告知预算与强制预算是两层工作

状态里的剩余次数帮助模型选择可完成的动作。真正限制调用次数的代码仍在 `WeatherAgent` 中：同批请求超过剩余工具预算时整批停止；最后一次模型调用提出工具请求时，不再执行无法交回下一轮的动作。

只写「最多调用 12 次」而不计数，不能保证预算生效。只在 Java 硬停止而不告知剩余预算，也可能让模型继续提出无法完成的计划。本例提供两层机制，但没有测出状态快照改善真实模型成功率的幅度。

### 5.3 状态应来自执行结果

模型说「已经查完」不是完成记录。预算使用量来自应用计数，工具是否成功来自实际结果，失败不能登记成成功。

本例状态快照只包含能够从程序直接核对的调用计数、完整批次数和压缩标记，没有让模型生成一个未经校验的「已完成事项」列表。真实业务若要记录订单状态或外部写入结果，还需要对应业务事实来源，不能从模型自述推导。

## 6、压缩历史时，什么可以整理

### 6.1 先定义保留条件

上下文压缩不是简单删除最早几条消息。旧消息里可能有用户原始要求、地点选择依据、唯一一次成功天气结果或关键失败。

本例 compact 模式的目标限于当前天气查询：保留原始问题和固定规则；对于相同工具和参数保留最新成功观察；失败尝试单独记录；最近一个工具批次保持原有协议消息。

「最新成功观察」不是完整天气历史。如果任务要比较不同更新时间的预报变化，就不能沿用这种整理策略。当前项目没有提供历史天气或跨快照变化研究功能。

### 6.2 应用历史与模型视图分开

`WeatherContext` 在 Java 中保留所有完整批次。压缩改变的是下一轮发送视图，原始工具记录仍在运行报告中。

这种分离有两个用途：一是可以解释压缩前发生过什么，二是可以重新核对被保留下来的内容。如果先永久删除唯一原始记录，再让模型对摘要作答，就很难判断错误来自工具、摘要还是生成。

这里没有持久化任务恢复。报告保存在磁盘，也不意味着程序支持中断后接着执行；恢复还需要明确任务位置、已执行动作及其可重放条件。

### 6.3 当前实现怎样整理完整批次

当前实现使用确定性整理，不调用模型生成摘要：

1. 消息视图 JSON 长度超过 6000 个 UTF-16 单元，且已有至少两个完整批次时，尝试构造候选视图。
2. 按工具名和参数整理最新成功返回，保留原始结果对象；错误记录独立保存。
3. 最近批次已经携带的成功结果不在检查点中重复放入。
4. 把检查点放在最近完整批次之前，再附上当前状态。
5. 只有候选视图确实短于完整历史时才采用，否则保留完整历史。

6000 是本例的本地字符阈值，不是模型窗口上限，也不是推荐所有项目使用的配置。检查点本身也有字段和文字开销，短任务不压缩可能更合理。

### 6.4 压缩后的信息仍需要验证

缩短了输入，不能单独说明压缩正确。还要检查正确地点与目标日期是否保留，概率的 null 是否仍为 null，单位和来源是否仍在，失败是否没有被改成成功，以及最近调用与返回是否完整配对。

这些可以先用本机替身做确定性验证。至于模型是否更容易完成任务，需要另外运行真实模型对照。输入更短也不保证总成本更低：如果压缩使模型重新查询已经取得的信息，总调用量反而可能增加。

## 7、Skills 与长期记忆放在什么位置

当规则不断增长时，可以把专门的处理方法放进 Skills，先提供目录，需要时再加载正文。需要区分两类内容：Skill 提供如何工作的指导，天气工具提供这次实际取得的数据。

weather-agent 当前把任务方法保存在 `WeatherPrompts` 中，没有实现 Skills 加载器。要观察已有的按需加载机制，可继续运行 first-agent 的[历史实验](archive/03-context-engineering-docs.md)，不要把那个文档案例中的已验证功能说成已经迁移到了天气项目。

同样，本轮查询的地点集合和执行历史都只属于当前任务。用户偏好是否值得保存、何时读取、如何纠正与删除，属于[下一篇的用户记忆](05-user-memory-knowledge-base.md)。把所有天气返回长期保存下来，不会自动形成可靠的用户记忆。

## 8、用运行记录检查机制

### 8.1 先完成真实工具检查

按[项目说明](weather-agent/README.md)构建后，在模块目录运行：

```powershell
java '-Dfile.encoding=UTF-8' -jar target/weather-agent-0.0.1-SNAPSHOT.jar --weather-check
```

这个入口不调用模型，只确认真实城市与天气接口可用。报告包含本次实际返回。数据会变化，不能拿文章里某个固定温度作为服务成功的判断标准。

### 8.2 固定提示词，再选择上下文策略

配置模型后运行一个公开教学问题：

```powershell
java '-Dfile.encoding=UTF-8' -jar target/weather-agent-0.0.1-SNAPSHOT.jar '--ask=比较北京市和上海市明天的天气，分别给出目标日期、降水概率和来源。' --prompt=rules --context=full
```

下一次只把 full 改为 state，或按需要改为 compact。每次运行都会显式调用模型，产生相应用量。真实天气没有冻结，两个报告如果数据不同，应先记录这个差异，不直接归因于上下文策略。

如果 compact 模式的 `compacted` 始终为 false，先看历史是否达到阈值、整理是否有收益。任务很短时不触发是正常行为，不应让真实模型重复查天气来凑出更漂亮的压缩数字。

### 8.3 报告按什么顺序读

把终端打印的真实报告路径填入以下命令：

```powershell
$reportPath = Read-Host '请输入终端打印的 report.json 完整路径'
$report = Get-Content -LiteralPath $reportPath -Encoding UTF8 -Raw | ConvertFrom-Json
$report.rounds | Select-Object round, messageJsonUtf16Units, compacted, elapsedMs
$report.toolEvents | ConvertTo-Json -Depth 30
$report.rounds[-1].messages | ConvertTo-Json -Depth 30
```

先看首轮有没有提前混入天气事实，再看搜索和天气结果是否进入后续请求。随后检查状态是否只有一个最新快照；发生压缩时，检查保留条件是否成立。最后看候选答案是否与这些实际输入一致。

仅运行 `--weather-check` 时没有模型轮次，报告没有 `rounds`；此时只读取 `toolEvents`。不要把空的模型轨迹理解为模型没有调用工具，这个入口本来就没有调用模型。

### 8.4 已完成什么验证

2026-10-19，天气项目在 JDK 21 下完成编译与打包。41 项本机断言检查了参数、地点隔离、未知值、错误返回、整批预检、调用预算、配对关系和压缩保留条件。其中使用真实 Spring AI HTTP 适配器对接本机模型替身，验证了三轮请求及天气结果回填；另外检查了打包后 Spring 入口的模型配置传递、无参数启动和非法模式拒绝。

另外运行打包后的 Java `--weather-check`，真实 Open-Meteo 城市检索与天气查询成功。这项证据说明本机当次外部接入可用，不代表所有网络环境或未来时刻都可用。

本机检查使用的天气值和模型回复是明确标记的替身；正式入口使用真实天气。尚未验证真实模型回答质量、Token 节省或服务端缓存命中，不引用旧文档案例的统计作为天气案例成绩。具体结果与验证入口见[项目说明](weather-agent/README.md)。

## 9、下一步：任务结束之后保存什么

到这里，天气助手已经能在一项任务中取得真实观察、组织下一轮输入、表达当前进度，并在适用条件下整理历史。它还没有跨会话记忆，也没有持久化恢复能力。

下一篇[《用户记忆与知识库》](05-user-memory-knowledge-base.md)回到第 02 篇已经实现的资料助手，研究任务之外的信息生命周期：哪些用户信息值得保存，知识怎样检索与更新，以及旧信息何时不应继续使用。
